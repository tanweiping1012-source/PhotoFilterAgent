# 照片筛选 Agent

旅行回来 473 张照片，要挑出 6 张。这个 agent 跑在 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 上，
自己决定看哪些、看多细、什么时候够了。

原图全程只读。

---

## 解决什么问题

挑照片真正难的不是"给照片打分"，是**注意力该花在哪**。

- **本地算得出来的东西和"好照片"几乎无关。** 实测：按清晰度/宽容度/过曝排名，
  系统选的 6 张与用户人工精选的 20 张**重合 0 张**，低于随机期望（0.39）。
  人工精选散布在系统排名第 20 到第 302 名之间——你选的是表情、是瞬间，本地分析器看不见。
- **但全部交给视觉模型看，又贵又慢。** 473 张全用高清档，是几十分钟和一笔不小的账单。

所以真正的问题是：**哪些照片值得花钱看，值得看多细。**

一条固定流水线回答不了——它只能对每张照片花掉完全等量的一次注意力。
而这显然是错的：有些照片 2 秒就该毙掉，有些值得看三遍再定。

## 安装

```bash
git clone https://github.com/tanweiping1012-source/photo-curator-agent.git
cd photo-curator-agent
./install.sh
```

脚本幂等，会自动克隆并构建 harness（已有则复用）、构建 Swift 引擎、装配 profile、自检。

**要求**：macOS（分类走 Apple Vision）· Swift 6.0+ · Node ^22.19 或 >=24 · pnpm

**视觉模型 Key** 写进 `~/.dsh/.credentials.yaml`：

```yaml
version: 1
refs:
  MINIMAX_CN_API_KEY: 你的key
```

harness 的循环模型走同一个 Key，`~/.dsh/settings.yaml`：

```yaml
llm-pi-ai:
  providers: { minimax-cn: { apiKeyEnv: MINIMAX_CN_API_KEY } }
agent-default-model: { provider: minimax-cn, model: MiniMax-M3 }
```

### 用

```bash
./run.sh ~/Desktop/照片 50 3 3 ~/Desktop/精选
#         目录          取样 人物 风景 导出目录
```

图形界面（前台常驻）：

```bash
cd ~/deepseek-harness && pnpm dsh --profile photo-web
# http://127.0.0.1:3080
```

## 一次运行，每一步谁在干活

同一个模型 **MiniMax-M3** 扮演两个角色，拿到的东西完全不同：

| 角色 | 看到什么 | 输出什么 |
|---|---|---|
| **大脑**（agent loop 里的模型） | **只有文字**——候选表、当前排名、切线分差 | 下一步调哪个工具 |
| **眼睛**（工具内部调用） | **只有一张图**+ 打分提示，不带任何对话历史 | 五个维度的分数 |

大脑**从头到尾没看过一张照片**。会话日志里 `data:image` / `base64` / `image_url`
出现 **0 次**——而 harness 的规矩是"进入模型请求的一切都必须可从日志重建"，
所以这是可验证的事实，不是承诺。

### 1. 你发出请求

```
帮我筛选 ~/Desktop/照片，只处理前 30 张。人物保留 2 张、风景保留 2 张。
```

### 2. 大脑读懂任务，让本机去分析——不联网

大脑（MiniMax-M3）决定第一步调 `analyze_folder`。这一步**没有模型看图**，
是一个独立的 Swift 进程在本机干活：

- Apple **Vision** 判定人物/风景
- **感知哈希**把画面高度相似的聚成连拍组
- 算清晰度、动态范围、过曝欠曝
- **人脸拍摄质量分 + 双眼纵横比判睁闭眼**

30 张、几秒钟、零成本。产出交给大脑的是一张**纯文本表**：

```
p001 风景 清晰79 宽容100 过曝18 +9878s
p289 人物 清晰47 宽容95 过曝5 连拍F25 脸质量62 眼睛睁30 +22360s
p296 人物 清晰45 宽容99 过曝10 连拍F26 脸质量41 ⚠硬伤:闭眼 +22554s
…
```

没有文件名、没有路径、没有绝对拍摄时间——只有匿名 ID 和相对秒数。

**`⚠硬伤:闭眼` 是本机算的，一分钱没花。** 全库 473 张跑一遍，280 张检出人脸、
其中 **27 张判定闭眼**。判据是眼睛轮廓的高/宽比：实测同一组人像里闭眼的是
0.15 / 0.12 / 0.09，睁眼的是 0.31 / 0.48 / 0.48，中间空档很宽，阈值取 0.22。

之所以要在本机把这件事算死，是因为**模型自己不会把闭眼当缺点**。上一版实测里
它给一张闭眼照的"瞬间"打了 72 分，评价原文是「闭目瞬间富有感染力」——
它看清了、明说了、然后**加了分**。不是模型看不见，是标准里没有"硬伤"这个概念。

### 3. 先解决连拍：默认折叠，不比不放行

连拍组**默认是折叠的**——每组只有一张露在候选池里，其余根本不参与竞争。
大脑想动它们，必须显式调 `compare`。

这是被实测逼出来的设计。上一版折叠是可选的，结果模型**一次 `compare` 都没调**，
78 组连拍全部无视、每张单独按绝对标尺打分——而连拍恰恰是"哪张睁着眼"
唯一能被可靠判出来的地方。**能绕过的约束等于没有约束**，所以改成默认生效。

代表也不是随便挑的。最早的版本按 ID 顺序取第一张，等于随机指定一张当门面——
全库跑下来 39 个组里有 **2 个组的门面本身就是闭眼照**（那正是要修的 bug 换了一层
重新出现）。现在按本机免费事实排：**先排除闭眼，再看人脸质量，再看清晰度**，
ID 兜底保证跨机器确定。改完之后**闭眼代表 2 → 0**，候选池大小不变，一分钱没多花。

大脑对每组调 `compare`。工具做的事：

1. 让 Swift 引擎把这几张各生成一张 **512px 无元数据 JPEG**
2. 把它们**一次性**发给眼睛（MiniMax-M3），问"哪张最好"
3. 只把一行结论交回大脑

> `F03` 胜者 `p011`：另外两张一个眨眼，一个手挡住下巴

**为什么这里用比较而不是打分**：同一组连拍的差别在眼神、表情、手的位置。
绝对打分给不出这种区分度——三张都会拿到 63、64、63。摆在一起比就分得出。

**为什么用 512px**：比较只需要**相对**判断，不需要辨认细节。这是最便宜的一档。

6 组比完，大脑调 `resolve_family` 定下代表，同组其余退出候选。**30 张 → 21 张。**

### 4. 粗排：21 张全部用 512px 打一遍

大脑调 `inspect(detail=low)`。工具对每张：

```
Swift 引擎 → 512px 无元数据 JPEG → 眼睛（独立请求，不带对话历史）
          ← {"dimensions":{"moment":55,"composition":62,…}}
```

**并发 4 路**（可配置）。这些请求彼此独立，串行等于把等待时间叠加——
实测 8 张串行 37 秒，并发后 11.8 秒。

**人像和风景用两套不同的标尺。** 人像那套把**闭眼、遮挡、脸失焦、表情失真**
明列为硬伤，命中任意一条就要求主体分 <40、瞬间分 <45，并明确禁止用
「自然」「不摆拍」「有情绪」「闭目沉思」这类理由抬分。风景那套不需要这些。

总分不由眼睛给，由本地按权重算：`(2×加权和 + 权重和) / (2×权重和)`，
整数运算，跨机器可复现。

交回大脑的仍然只是文字：

```
p001  总分 58 [瞬55 构62 主58 光65 叙50]  雪林小径氛围安静，构图平淡
```

**为什么全部用便宜档**：这一步的目的是**砍掉明显不行的**，不是排出精确名次。
21 张里有一多半会在这一步就出局，为它们花高清档的钱是浪费。

### 5. 大脑自己判断：还要不要花钱

调 `status`，拿到的是一份**渲染出来的处境摘要**（不是历史回放）：

```
【人物】目标 2 · 候选 13 · 已看 13
  当前前 2: p029(66) p026(63)
  切线分差 3   稳定
【风景】目标 2 · 候选 8 · 已看 8
  当前前 2: p005(66) p008(65)
  切线分差 1   ⚠ 不稳，值得再看
```

**切线分差 = 第 N 名和第 N+1 名的分差**，直接回答"还要不要继续花钱"：

- 差 6 分 → 稳。再看也不会改变名次，**别花这个钱**
- 差 1 分 → 不稳。这个名次是噪声决定的，**值得放大看**

### 6. 精排：只对切线附近那几张用 1536px

大脑对切线上下那几张调 `inspect(detail=high)`。同一条路径，只是引擎生成的是
**1536px**——能看清表情、纹理、对焦是否真的在眼睛上。

这一步经常翻盘：

> `p014` 粗排第二（64 分），1536px 看完跌到 51——典型"到此一游"纪念照，
> 小图看着还行，放大就露馅

同一张照片如果已经有 ≥ 该档位的分数，工具**直接返回缓存、不计费**，
并在结果里明说"（缓存，未计费）"。

### 7. 大脑提交名单，代码来校验

调 `propose`。**校验是代码做的，不是模型自觉**：

1. 都在候选池里
2. 不超过保留目标
3. 同一连拍组不超过一张
4. **每张都必须被 inspect 过**——防止推荐一张从没打开过的照片
5. 每张有理由

不过就把**原因**回灌给大脑，让它改了再提。

### 8. 你确认后才复制

```
| 人物 | DSCF9525.JPG | 66 | 冰原侧身人像，构图最好 |
| 人物 | DSCF9430.JPG | 63 | 冰原人像，纪实感强 |
| 风景 | DSCF8915.JPG | 66 | 雪山与云层信息丰富 |
| 风景 | DSCF9251.JPG | 65 | 雪港冬景层次分明 |

花费：26 次打分 + 6 次比较
```

匿名 ID 在这一步才映射回真实文件名——映射表只存在本机工作目录。
`export_selection` **只复制**：原图不移动、不删除、不改名、不写回。

### 尺寸策略小结

| 档位 | 像素 | 用在哪 | 为什么 |
|---|---|---|---|
| **512px** | 最长边 | 连拍比较 · 全池粗排 | 比较只要相对判断；粗排只要砍掉明显不行的 |
| **1536px** | 最长边 | 只有切线附近 | 名次被噪声决定时，才值得看清表情和对焦 |

**一句话**：便宜的钱花在"排除"，贵的钱花在"决定"。

## 跟 App 版本的差别

前身是 [PhotoFilter](https://github.com/tanweiping1012-source/PhotoFilter)，一个 macOS 原生 App。
它是一条**流水线**，这个是 **agent**。区别不在界面：

| | PhotoFilter（App） | 这个 agent |
|---|---|---|
| **谁决定看哪些** | 320 行写死的规则挑出 48 张 | 模型看着候选表自己决定 |
| **每张看多细** | 全部同一档，第 1 名和第 48 名花一样的钱 | 按需 low/high，只在切线花贵的 |
| **连拍组代表** | **最锐的赢**——技术指标选 | **真的比一次**——`compare` |
| **循环形态** | `for`，计划在第一次联网前就冻结 | 下一步取决于上一步看到了什么 |
| **模型知道目标吗** | 不知道，只收到"给这张打 5 个分" | 知道要留几张，还看得见切线分差 |
| **比较** | 校验器主动拉黑"相比/更好/名次" | `compare` **主动解禁**——比较正是它存在的理由 |
| **形态** | macOS 原生 App | harness 插件 + 独立 Swift CLI |

最实质的是**连拍组代表**。App 用"谁最锐"糊弄过去了，但同一组连拍的差别根本不在清晰度，
在一个眼神、一只手的位置。绝对打分给不出区分度，两张摆在一起比就可以。

App 那套本地分析引擎原样移植了过来（感知哈希、相似聚类、Vision 人物分类、清晰度曝光），
在这里降级成 agent 的**免费工具**——不再决定谁能进候选池，只回答"有哪些照片、各自什么底子"。

## 已验证

在 473 张真实旅行照片上：

| | |
|---|---|
| **人物/风景分类** | **99.6%**（471/473），人物精确率 100%。真值取自用户自己的目录结构 |
| 全量本地分析 | **14 秒**，不联网、不花钱 |
| **闭眼判定** | 标定样本 **5/5 全对**；全库免费标出 **27 张**（280 张检出人脸中） |
| **连拍折叠** | 39 组覆盖 426 张 → 候选池 **473 张缩到 86 张**，全程零成本 |
| **组代表不再闭眼** | 修复前 39 个代表里 2 个是闭眼照，修复后 **0 个** |
| **原图安全** | 导出前后 473 个源文件**逐字节完全一致** |
| 打分并发 | 8 张从 37.2 秒降到 **11.8 秒** |
| 跨会话缓存 | 同一张同档位**只付一次钱** |

修复后重跑那次实测：**不给任何策略提示**，大脑自己把三张闭眼照当硬伤排除、
调了 1 次 `compare`，只花了 2 次 `inspect`（修复前同样场景花 6 次）。

## 隐私边界

由**工具集本身**保证，不依赖 agent 自觉——两个 profile 都关掉了 harness 的全部通用
文件系统与 shell 工具（`tool-bash` / `tool-fs` / `tool-fs-search` / `skill-filesystem`
/ `str-replace-editor` / `tool-web`）。

> 实测轨迹里模型尝试过 `read_image` 直接读原图。那会把全分辨率、带 EXIF 与 GPS 的
> 原图送进对话，绕过引擎的匿名化、降采样和元数据剥离。

发出去的只有引擎生成的无元数据缩放 JPEG（512/1024/1536px）。文件名、路径、GPS、
绝对拍摄时间都不出本机——匿名 ID 到真实路径的映射只存在于本地工作目录。

## 已知限制

1. **策略部分来自任务提示。** `run.sh` 把六步写进了任务文本。不过闭眼修复后的那次
   实测是**不给策略提示**跑的，大脑自己排除了硬伤、自己调了 `compare`——说明把约束
   放进工具描述与候选表（而不是任务文本）之后，它能自己走对。**但只验证过这一次。**
2. **连拍折叠很激进，且它挡住的主要是人物照。** 全库 307 张人物照被 14 个组吃掉
   302 张，折叠后候选池里只剩 **17 张人物**。这确实是目前唯一的免费剪枝手段
   （473→86），但一个 49 张的"组"已经不是连拍而是整段场景——**这段里最好的那张
   未必就是代表**。而 `compare` 一次只收 2–4 张，49 张的组没法一次比完。
3. **除折叠之外没有别的剪枝。** 折叠后剩下的 86 张，粗排阶段是**全部**用 512px
   打一遍。前身 App 里"本地规则先挑 48 张"那个守门人被拿掉了，没有等价替代。
4. **分级授权没做。** 设计里 `propose` / `export_selection` 应当弹确认，目前直接执行
   （不过 `export` 只复制，最坏是多一份副本）。
5. **选片质量只在小样本上量过**，不构成统计结论。**本地技术指标与人工精选的重合度
   实测接近于零**——清晰度、宽容度这些排出来的名次和人的口味基本无关，
   所以它们只用来描述底子，不用来决定名次。
6. **全量 473 张的视觉策展没跑过**，验证到 50 张取样。
7. **DeepSeek Harness 是 v0.1 developer preview**，会有破坏性变更。
   本仓库锚定 `dsh-v0.1.1-rc.2`（`b150a55`）。

## 结构

```
engine/     Swift：分析引擎 + CLI（analyze / select / preview / resolve / export）
  PortraitQualityAnalyzer.swift  人脸质量分 + 双眼纵横比判睁闭眼（本地、免费）
agent/      TypeScript：cordis 插件
  index.ts    9 个模型可见工具
  state.ts    运行状态、切线分差、提议校验、跨会话持久化
  vision.ts   视觉客户端（工具自己调，图片不进对话历史）
  pool.ts     有界并发
profiles/   两个 profile 模板（install.sh 替换占位符后装进 $DSH_HOME）
bench/      评测脚本 · install.sh 从零装配 · run.sh 一键运行
```

**为什么视觉调用在工具里而不是交回给循环**：图片一旦进对话历史，之后每一轮都要重发。
100 次打分就是 100 份图片反复穿过上下文。工具自己调、只交回一行紧凑分数，历史里就只剩数字。
