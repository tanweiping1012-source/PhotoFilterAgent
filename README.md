# 照片筛选 Agent

旅行回来一堆照片，你想挑出最好的几张——但翻到第 200 张就烦了。

这个程序替你翻。翻完把选中的**复制**到一个新文件夹，附上每张为什么被选中。
你的原照片一个字节都不会动。

只能在 **macOS** 上跑。

## 先看它怎么用

你打开一个对话框，用大白话说：

> 帮我从 `~/Desktop/冰岛` 里挑照片，人物留 3 张、风景留 3 张。

然后它开始干活。过程你全程看得见，大致长这样：

```
已在本机分析 473 张：人物 307 · 风景 166。
⚠ 发现 39 组几乎一样的照片，已默认折叠——每组只露一张出来竞争。
⚠ 本机已判定 27 张人物照眼睛闭着。这是硬伤，不选它们。

正在比较第 1 组的 4 张 …… 选中第 3 张（另外三张：一张眨眼、一张手挡住下巴）
正在给 86 张打分（小图，快）……
【人物】目标 3 · 当前前 3 分差 1 分 → 名次不稳，值得看清楚点
正在把这 5 张放大到高清重看 ……
```

最后给你一张表：

| 类别 | 文件 | 分数 | 理由 |
|---|---|---|---|
| 人物 | DSCF9525.JPG | 66 | 冰原侧身人像，构图最好 |
| 人物 | DSCF9430.JPG | 63 | 冰原人像，纪实感强 |
| 风景 | DSCF8915.JPG | 66 | 雪山与云层层次丰富 |

你说"可以"，它才复制文件。

## 它和"自动选片脚本"差在哪

大部分自动选片工具是**流水线**：一套写死的规则，每张照片走一模一样的流程、
花一模一样的力气。第 1 名和第 300 名得到的对待完全相同。

这个不一样。它每做完一步会**停下来看结果，再决定下一步**——

- 这两张几乎一样？那就直接比一次，别分别打分
- 这张一眼就不行？扔掉，别在它身上花钱
- 第 3 名和第 4 名只差 1 分？那这个名次是蒙的，**放大重看**
- 前三名遥遥领先？**够了，收工**，别再花钱

这种"自己决定下一步做什么"的程序，就是**agent**。
它和脚本的区别不在界面，在于**下一步取决于上一步看到了什么**。

> **为什么这件事重要**
>
> 挑照片真正难的不是"给照片打分"，是**注意力该花在哪**。
>
> 让 AI 把每张照片都仔细看一遍当然准，但 473 张全用高清档，
> 是几十分钟外加一笔不小的账单。而这笔钱大部分是浪费的——
> 一多半照片两秒钟就该毙掉。

### 它靠什么跑起来

底座是 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)，
一个开源的 agent 运行环境，负责跟 AI 对话、记账、管调用、存记录。

我们**没有重写它**，只是往里插了一个**插件**，教会它一件它本来不会的事：怎么看照片。
插件里装了 9 个"动作"（分析目录、比较两张、给一张打分、导出……），
AI 想干什么就从里面挑一个来调。

## 安装

### 你需要先有

| | 怎么确认 | 没有的话 |
|---|---|---|
| **macOS** | — | 换不了，人脸识别用的是苹果自带的能力 |
| **Xcode 命令行工具** | `swift --version` | `xcode-select --install` |
| **Node.js** | `node --version` ≥ 22.19 | [nodejs.org](https://nodejs.org) |
| **pnpm** | `pnpm --version` | `npm install -g pnpm` |
| **一个 AI 的 API Key** | 见下 | 没有也能跑，但只剩纯本地选片 |

### 装

```bash
git clone https://github.com/tanweiping1012-source/photo-curator-agent.git
cd photo-curator-agent
./install.sh
```

脚本会自动克隆并构建 harness、编译本地分析引擎、装好配置、跑一遍自检。
**可以重复执行**，只补缺的部分，不会把已有的搞坏。

### 配 API Key

这个程序要用一个**能看图的 AI**（这里用的是 MiniMax-M3）来判断照片好不好。
调用它需要一把 Key，去服务商网站注册后拿到。

Key 写进 `~/.dsh/.credentials.yaml`：

```yaml
version: 1
refs:
  MINIMAX_CN_API_KEY: 你的key
```

再告诉 harness 用哪个模型，写进 `~/.dsh/settings.yaml`：

```yaml
llm-pi-ai:
  providers: { minimax-cn: { apiKeyEnv: MINIMAX_CN_API_KEY } }
agent-default-model: { provider: minimax-cn, model: MiniMax-M3 }
```

> **大概要花多少钱**：钱花在"让 AI 看一张图"上，一次一张小图。
> 实测一次 30 张照片的完整筛选，花了 26 次打分 + 6 次比较。
> 单价看服务商定价——这个程序整套设计就是围绕**怎么少调几次**转的。

### 跑

**图形界面**（推荐第一次用）：

```bash
cd ~/deepseek-harness && pnpm dsh --profile photo-web
```

然后浏览器打开 `http://127.0.0.1:3080`，像聊天一样提要求。

> ⚠️ 这个命令会**占住终端窗口**，别关它，也别在这个窗口里再敲别的命令
> ——敲进去的字会被它当成输入吃掉。要跑别的命令请新开一个窗口（⌘N）。

**命令行**（一条命令跑完）：

```bash
./run.sh ~/Desktop/冰岛 50 3 3 ~/Desktop/精选
#         照片目录       │  │ │  └ 选中的复制到哪
#                        │  │ └── 风景留几张
#                        │  └──── 人物留几张
#                        └─────── 只处理前几张（先小规模试跑）
```

## 它在背后是怎么想的

### 先说一件反直觉的事

同一个 AI（MiniMax-M3）在这里被用在**两个完全不同的岗位**上，看到的东西天差地别：

| 岗位 | 它能看到什么 | 它负责什么 |
|---|---|---|
| **决策者** | **一个字都是文字**——照片清单、当前排名、分差 | 决定下一步调哪个动作 |
| **打分员** | **只有一张图**和一份打分标准，不知道前因后果 | 给这一张打分 |

**做决定的那个 AI，从头到尾没看过任何一张照片。**
它只读一张纯文字的表格，像看一份 Excel。

看图的那个 AI 每次只看一张，也不知道自己在干一件什么大事——
它拿到一张图，吐出五个分数，就结束了。

> **为什么要这么拆**：图片一旦进了对话历史，之后每一轮都要重发一遍。
> 打 100 次分就是 100 份图片反复在上下文里穿来穿去，又慢又贵。
> 让"打分"这个动作自己去调 AI、只交回一行数字，历史里就只剩文字。

---

### 第 1 步 · 本机先扫一遍（不联网、不花钱）

决策者收到你的要求，第一件事是调 `analyze_folder`。
这一步**没有任何 AI 看图**，是一个独立的本地程序在干活：

- 判断这是**人物照**还是**风景照**
- 把**看起来几乎一样**的照片归成一组（同一个场景连拍了一串）
- 算清晰度、明暗层次、有没有过曝
- 检测人脸，并判断**眼睛是睁着还是闭着**

> 这四件事里，苹果系统只帮忙做了一部分，剩下的是这个项目自己写的算法。
> 具体谁做了什么 → [苹果帮了多少忙，我们自己写了多少](#苹果帮了多少忙我们自己写了多少)

473 张，**14 秒**，零成本。

交给决策者的是一张**纯文字表**，长这样：

```
p001 风景 清晰79 宽容100 过曝18 +9878s
p289 人物 清晰47 宽容95 过曝5 连拍F25 脸质量62 眼睛睁30 +22360s
p296 人物 清晰45 宽容99 过曝10 连拍F26 脸质量41 ⚠硬伤:闭眼 +22554s
```

注意这里**没有文件名、没有路径、没有拍摄时间**——只有 `p001` 这样的编号，
和"距第一张多少秒"。真实文件名到编号的对照表只存在你自己的电脑上。

#### 关于那个"眼睛闭"的标记

这是**本机免费算出来的**，一分钱没花。
判断方法是量眼睛轮廓的**高度除以宽度**：睁开时这个比值明显大，闭上时明显小。
实测同一组人像里，闭眼的三张是 0.15 / 0.12 / 0.09，睁眼的三张是 0.31 / 0.48 / 0.48，
中间空档很宽，所以阈值取 0.22。全库 473 张里，280 张检出人脸，**27 张判定闭眼**。

**为什么非要本机算，不能交给 AI 自己看？**

因为实测发现——**AI 根本不觉得闭眼是缺点**。

早期版本里，它给一张闭眼照的"瞬间感"打了 72 分（满分 100），
评价原文是「闭目瞬间富有感染力」。

它看清了，它明说了，然后它**加了分**。

问题不在于 AI 眼神不好，在于我们给它的打分标准里**压根没有"废片"这个概念**。
所以现在改成：本机把事实算死，直接写在表上，不给它自由发挥的空间。

---

### 第 2 步 · 几乎一样的照片，先比不打分

上一步找出的"看起来几乎一样"的那些组，**默认是折叠的**——
每组只有一张露在候选名单里，其余的根本不参与竞争。
决策者想动它们，必须明确地调"比较"这个动作。

**为什么要强制？** 因为早期版本里折叠是可选的，结果 AI **一次比较都没调**，
78 组连拍全被无视、每张单独打分。而连拍恰恰是唯一能可靠判出
"哪张睁着眼"的地方——三张里两张闭眼，摆一起一眼就看出来，
分开打分则会各自拿到 63、64、63。

**能绕过的约束等于没有约束**，所以改成默认生效。

比较是这么做的：本地把这几张各生成一张 **512 像素的小图**，
一次性发给 AI 问"哪张最好"，只把一行结论收回来：

> 第 3 组的胜者是 `p011`：另外两张一个眨眼，一个手挡住下巴

**为什么用比较而不是打分**：同一组照片的差别在眼神、表情、手的位置。
绝对打分给不出这种区分度，摆在一起比就分得出。

**为什么只用 512 像素**：比较只需要判断"谁更好"，不需要看清细节。这是最便宜的一档。

比完之后同组其余照片退出竞争。全库实测：**473 张缩到 86 张**，全程零成本。

> **一个没修干净的坑**
>
> 折叠时"留哪一张当代表"，最早的版本是按编号顺序留第一张——
> 等于随机指定一张当门面。全库跑下来，39 个组里有 **2 个组的门面本身就是闭眼照**。
>
> 也就是说：那个"挑出来全是闭眼照"的毛病，换了一层又冒出来了，
> 而且更糟——AI 连给它打分的机会都没有，它直接以代表身份进了名单。
>
> 现在改成按本机已经算出的免费事实排：**先排除闭眼，再看人脸质量，再看清晰度**。
> 改完之后闭眼代表 **2 → 0**，候选池大小不变，一分钱没多花。

---

### 第 3 步 · 粗排：全部用小图快速过一遍

剩下的 86 张，每张生成一张 512 像素小图发去打分。
**4 张同时进行**——这些请求互不相干，一张张排队等于把等待时间叠加起来。
实测 8 张：串行 37.2 秒，并发 **11.8 秒**。

**人物照和风景照用两套不同的打分标准。**
人物那套把**闭眼、遮挡、脸失焦、表情失真**明确列为硬伤，
命中任意一条就必须打低分，并且明确禁止用「自然」「不摆拍」「有情绪」「闭目沉思」
这类理由往上抬分。风景那套不需要这些。

打分员只给五个维度的分，**总分由本地按权重算**——整数运算，换台电脑结果一样。

收回来的仍然只是文字：

```
p001  总分 58 [瞬55 构62 主58 光65 叙50]  雪林小径氛围安静，构图平淡
```

**为什么这一步全用便宜档**：这一步的目的是**淘汰**，不是排名次。
86 张里一多半会在这里出局，为它们花高清的钱是浪费。

---

### 第 4 步 · 停下来算一笔账：还值不值得继续花钱

决策者调"看看现在什么情况"，拿到的是一份**当场算出来的处境摘要**：

```
【人物】目标 2 · 候选 13 · 已看 13
  当前前 2: p029(66) p026(63)
  第 2 名和第 3 名差 6 分   → 稳
【风景】目标 2 · 候选 8 · 已看 8
  当前前 2: p005(66) p008(65)
  第 2 名和第 3 名差 1 分   → ⚠ 不稳，值得再看
```

关键就是那个**分差**——第 N 名和第 N+1 名之间差多少（N 就是你要留几张）。
它直接回答"还要不要继续花钱"：

- **差 6 分** → 稳。再怎么看名次也不会变，**别花这个钱**
- **差 1 分** → 不稳。这个名次基本是噪声决定的，**值得放大看**

---

### 第 5 步 · 精排：只有分差不稳的那几张，才配用高清

对着分界线上下那几张，重新生成 **1536 像素**的大图再看一遍——
这个尺寸能看清表情、纹理、对焦到底有没有落在眼睛上。

这一步经常翻盘：

> `p014` 粗排排第二（64 分），高清看完跌到 51——
> 典型的"到此一游"纪念照，小图看着还行，放大就露馅了

同一张照片如果之前已经用同等或更高的清晰度看过，**直接返回上次的结果，不重复计费**。

**尺寸策略一句话**：

| 档位 | 用在哪 | 为什么 |
|---|---|---|
| **512 像素** | 比较 · 全池粗排 | 比较只要相对判断；粗排只要淘汰 |
| **1536 像素** | 只有分差不稳的那几张 | 名次被噪声决定时，才值得看清表情和对焦 |

**便宜的钱花在"排除"，贵的钱花在"决定"。**

---

### 第 6 步 · 交名单，代码来把关

AI 提交最终名单时，**由代码做五项检查，不靠它自觉**：

1. 每张都还在候选名单里
2. 没超过你要的数量
3. 同一组几乎一样的照片，不能选出两张
4. **每张都必须真的被看过**——防止它推荐一张从没打开过的照片
5. 每张都得有理由

不通过就把**具体哪里错了**告诉它，让它改了再提。

### 第 7 步 · 你点头，才复制

编号在这一步才映射回真实文件名。
导出**只做复制**：原图不移动、不删除、不改名、不写回。

## 你的照片会被传到哪里去

这是最该问的问题，直说：

**会传出去的**：本地程序生成的**缩小过、去掉全部元数据**的 JPEG（512 / 1024 / 1536 像素），
发给 AI 服务商用于打分。

**不会传出去的**：原图、文件名、文件路径、GPS 位置、拍摄时间。

这不靠 AI 自觉，靠**把工具拿掉**：配置里关掉了 harness 自带的全部通用文件读写和
命令行工具（`tool-bash` / `tool-fs` / `tool-fs-search` / `skill-filesystem` /
`str-replace-editor` / `tool-web`）。它想绕也没有路。

> **为什么要关**：实测记录里，AI 真的尝试过用通用工具**直接读原图**。
> 那会把全分辨率、带 EXIF 和 GPS 的原图整个送进对话——
> 绕过所有的匿名化、缩小和元数据剥离。
>
> 关掉之后这条路就没了。

**做决定的那个 AI 一张照片都没看过**，这点是可验证的：
会话记录里 `data:image` / `base64` / `image_url` 出现 **0 次**。
harness 的规矩是"凡是送进 AI 的东西都必须能从日志里重建出来"，
所以这不是一句承诺，是可以自己去查的事实。

## 实测数据

在 473 张真实旅行照片上跑出来的：

| | |
|---|---|
| **人物/风景分类正确率** | **99.6%**（471 / 473），人物这一类精确率 100% |
| 全库本机分析耗时 | **14 秒**，不联网、不花钱 |
| **闭眼判定** | 标定样本 **5 / 5 全对**；全库免费标出 **27 张** |
| **折叠效果** | 39 组覆盖 426 张 → 候选从 **473 张缩到 86 张**，零成本 |
| **组代表不再是闭眼照** | 修复前 39 个代表里 2 个闭眼，修复后 **0 个** |
| **原图安全** | 导出前后 473 个源文件**逐字节完全一致** |
| 打分并发 | 8 张从 37.2 秒降到 **11.8 秒** |
| 重复运行 | 同一张同档位**只付一次钱** |

分类的"正确答案"取自用户自己的目录结构——他本来就把人物照和风景照分开放。

闭眼修复之后重跑了一次，**不给任何操作提示**：
AI 自己把三张闭眼照当硬伤排除、自己调了 1 次比较，
只花了 2 次打分（修复前同样场景花 6 次）。

## 它做不好什么

这一节不是免责声明，是实测发现的真问题：

1. **有些策略仍然是任务提示里教的，不是它自己想出来的。**
   命令行版把步骤写进了任务文本。虽然闭眼修复后那次是不给提示跑通的
   （说明把规则写进工具说明比写进任务文本管用），但**只验证过这一次**。

2. **折叠很激进，而且它挡住的主要是人物照。**
   全库 307 张人物照被 14 个组吃掉了 302 张，折叠后候选里**只剩 17 张人物**。
   一个 49 张的"组"已经不叫连拍了，那是**整段场景**——这段里最好的那张
   未必就是被留下的代表。而"比较"一次最多只收 4 张，49 张的组没法一次比完。

3. **除了折叠，没有别的省钱手段。**
   折叠后剩下的 86 张，粗排阶段是**全部**打一遍分。
   前身 App 里有个"本地规则先挑 48 张"的守门人，被拿掉了，没有等价替代。

4. **"高风险操作要先问你"没做。**
   设计上"提交名单"和"导出"应该弹确认，目前是直接执行的
   （不过导出只做复制，最坏结果是多一份副本）。

5. **选片质量只在小样本上量过**，不构成统计结论。
   另外有个**负面结果**要说清楚：**本地那些技术指标和人的口味基本无关**——
   按清晰度/宽容度/过曝排出来的前 6 张，和用户人工精选的 20 张**重合 0 张**，
   比随机还低。人工精选散落在系统排名的第 20 到第 302 名之间。
   你选的是表情、是瞬间，本地分析器看不见。所以这些指标只用来**描述底子**，不用来定名次。

6. **全量 473 张的完整视觉筛选没跑过**，验证做到 50 张取样。

7. **DeepSeek Harness 目前是 v0.1 开发者预览版**，官方明确会有破坏性改动。
   本仓库锚定在 `dsh-v0.1.1-rc.2`（`b150a55`）。换版本出问题，先回到这个版本。

## 苹果帮了多少忙，我们自己写了多少

有个很容易产生的误解：以为"判断人物照还是风景照"是调一个苹果的 API 就搞定的事。

**不是。苹果没有这个 API。**

### 苹果的 Vision 是传感器，不是判断者

Vision 是 macOS 自带的图像识别框架。它只吐**原始事实**，一个判断都不下：

| 我们问 Vision | 它只回答 |
|---|---|
| 有脸吗 | 有一张，框在这个位置，拍摄质量 0.53 |
| 有人吗 | 有个人体，框在这，置信度 0.71 |
| 人在哪些像素上 | 这是人物区域的掩码 |
| 有几个人 | 这几团像素分别属于不同的人 |
| 视线会落在哪 | 这是画面的视觉焦点分布图 |
| 眼睛在哪 | 这是眼睛轮廓的一串坐标点 |

注意它**一次都没说"这是人像照"**。它说的全是"这里有个东西"。

### 真正难的问题，Vision 一个都答不了

- 一个人站在冰川前，只占画面 2% ——**这算人物照还是风景照？**
- 三个游客路过入了镜——**这是合影还是风景照？**
- 眼睛轮廓的坐标拿到了——**所以眼睛到底闭没闭？**
- 这两张画面很像——**是同一个瞬间连拍的，还是不同时候拍了同一个地方？**
- 这张看起来不太锐——**是拍糊了，还是这个场景本来细节就少（干净的雪山、纯净的海面）？**

这些全是**自己写的算法**在回答。

### 代码上是什么比例

```
本地引擎总计 2534 行
├─ 完全不碰苹果框架   1624 行   64%
└─ 会调用 Vision 的     910 行   35%
     └─ 其中真正是 Vision API 调用的，只有十几行
```

最典型的是分类那个文件：**589 行代码里，出现苹果 API 的只有 14 行**，
剩下 575 行全是自己写的判定规则，带 15 个手工标定的门槛值：

```swift
脸小于画面 0.8%           → 不算人像
脸得在画面里足够占主导     → 门槛 0.42
超过 3 个人               → 不算"风景配人"
人得占据视觉焦点一半以上   → 门槛 0.50
```

**那个 99.6% 的分类准确率，是这层规则的成绩，不是 Vision 的成绩。**

### 完全自己写、一行苹果 AI 都没用的部分

| 做什么 | 怎么做的 |
|---|---|
| **找出"几乎一样"的照片** | 把每张压成 8×8 的灰度指纹，比对有多少格不同 |
| **把它们聚成组** | 低对比度的画面**不自动分组**——否则一堆过曝的白、纯色的天会被误当成同一张 |
| **算清晰度** | 见下，这个最有讲究 |
| **没有 API Key 时的纯本地选片** | 按百分位归一化排名，不联网也能出结果 |

#### 清晰度为什么不能直接算

这里三个决定都是踩过坑才定下来的：

1. **只统计最强的那一小撮边缘**，不用整张图的方差。
   因为大片天空、纯色背景会把全局统计**稀释掉**；
   而用固定分位（比如取前 10%）在边缘稀疏的画面里会直接落进平坦区域，读数变成 0。

2. **除以画面反差**做归一化。
   否则阴天的低反差场景和晴天的高反差场景根本没法放在一起比。

3. **只在同一组相似照片内部比较**，不跟全库比。
   否则一张干净利落的雪山风景，会因为"细节本来就少"被误判成拍糊了。

### 闭眼判定也是自己写的

苹果**没有**"检测眨眼"这个功能。它只给眼睛轮廓的坐标点。

从坐标到结论这一步是自己算的：量眼睛轮廓的**高度除以宽度**——
睁开时这个比值大，闭上时明显小。

阈值 **0.22** 是拿真实照片标出来的：闭眼的三张量出 0.15 / 0.12 / 0.09，
睁眼的三张是 0.31 / 0.48 / 0.48，中间空档很宽，取中央最稳。

（早期版本取 0.11，结果 0.15 和 0.12 那两张明明闭着的被判成睁开了。）

### 一句话

**苹果 Vision 负责"看见"，所有的"所以呢"都是自己写的。**

而准确率恰好就取决于后面那半。

## 名词表

| 词 | 意思 |
|---|---|
| **agent** | 能自己决定下一步做什么的程序，区别于按固定顺序执行的脚本 |
| **DeepSeek Harness** | 跑 agent 的开源底座：管对话、管工具调用、记日志 |
| **插件** | 往底座里加的一块能力。这个项目就是一个插件 |
| **工具 / 动作** | agent 能调用的一件具体事，比如"给这张打分""比较这几张" |
| **连拍组** | 画面看起来几乎一样的一串照片，被归成一组 |
| **折叠** | 一组里只留一张出来竞争，其余暂时不参与 |
| **候选池** | 目前还在竞争的照片 |
| **粗排 / 精排** | 先用小图快速淘汰，再用大图仔细看剩下的 |
| **分差** | 第 N 名和第 N+1 名的分数差，用来判断名次稳不稳 |
| **Apple Vision** | macOS 自带的图像识别框架。只报告"看见了什么"，不下判断 |
| **感知指纹** | 把一张照片压成 8×8 的灰度小方块，用来快速比对两张像不像 |

## 它的前身

这个项目改写自 [PhotoFilter](https://github.com/tanweiping1012-source/PhotoFilter)，
一个 macOS 原生 App。那个是**流水线**，这个是 **agent**：

| | PhotoFilter（App） | 这个 agent |
|---|---|---|
| 谁决定看哪些照片 | 320 行写死的规则挑出 48 张 | AI 看着清单自己决定 |
| 每张看多细 | 全部一个档，第 1 名和第 48 名花一样的钱 | 按需要，只在关键处花贵的 |
| 连拍组留哪张 | **谁最锐利谁赢**——纯技术指标 | **真的比一次**，让 AI 看着选 |
| 流程形态 | `for` 循环，计划在联网前就定死了 | 下一步取决于上一步看到了什么 |
| AI 知道目标吗 | 不知道，只收到"给这张打 5 个分" | 知道要留几张，也看得见分差 |

最实质的差别是**连拍组留哪张**。App 用"谁最锐利"糊弄过去了，
但同一组照片的差别根本不在清晰度，在一个眼神、一只手的位置。

App 那套本地分析引擎原样搬了过来，但在这里**降级成了免费工具**——
不再决定谁能进候选池，只负责回答"有哪些照片、各自什么底子"。
