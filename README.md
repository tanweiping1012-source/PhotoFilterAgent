# PhotoFilterAgent · 照片筛选 Agent

旅行回来几千上万张照片，你想挑出最好的几张——但翻到第 200 张就烦了。

这个程序替你翻。翻完把选中的**复制**到一个新文件夹，附上每张为什么被选中。
你的原照片一个字节都不会动。

只能在 **macOS** 上跑。

## 先看它怎么用

你打开一个对话框，用大白话说：

> 帮我从 `~/Desktop/冰岛` 里挑照片，人物留 3 张、风景留 3 张。

然后它开始干活。过程你全程看得见，大致长这样：

```
已在本机建立匿名候选与连拍家族。
偏好：通用 baseline；连拍保留策略：balanced。
正在用 low 小图评估全部人物候选，包括连拍中被旧视图折叠的成员……
精排计划：high 复核 12 张；双向 pairwise 最多 18 次调用。
（展示计划并确认费用后）按冻结计划只补未完成项目……
已冻结恰好 3 张人物名单，正在交给 independent_evaluator 做 audit v3……
audit v3：PASS。可以展示名单；尚未导出任何文件。
```

最后给你一张表：

| 类别 | 文件 | 分数 | 理由 |
|---|---|---|---|
| 人物 | DSCF9525.JPG | 66 | 冰原侧身人像，构图最好 |
| 人物 | DSCF9430.JPG | 63 | 冰原人像，纪实感强 |
| 风景 | DSCF8915.JPG | 66 | 雪山与云层层次丰富 |

你要求导出后，它先返回一次性确认码；只有你在新消息中精确确认，第二次调用才复制文件。

## 它和"自动选片脚本"差在哪（跟App版本的差异）

大部分自动选片工具是**流水线**：一套写死的规则，每张照片走一模一样的流程、
花一模一样的力气。第 1 名和第 300 名得到的对待完全相同。

这个不一样。它每做完一步会**停下来看结果，再决定下一步**——

- 这两张几乎一样？那就直接比一次，别分别打分
- 这张一眼就不行？扔掉，别在它身上花钱
- 第 3 名和第 4 名只差 1 分？那这个名次是蒙的，**放大重看**
- 前三名遥遥领先？**够了，收工**，别再花钱

这种"自己决定下一步做什么"的程序，就是**agent**。
它和脚本的区别不在界面，在于**下一步取决于上一步看到了什么**。

> **为什么这件事重要**
>
> 挑照片真正难的不是"给照片打分"，是**注意力该花在哪**。
>
> 让 AI 把每张照片都仔细看一遍当然准，但 473 张全用高清档，
> 是几十分钟外加一笔不小的账单。而这笔钱大部分是浪费的——
> 一多半照片两秒钟就该毙掉。

### 它靠什么跑起来

底座是 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)，
一个开源的 agent 运行环境，负责跟 AI 对话、记账、管调用、存记录。

我们**没有重写它**，只是往里插了一个**插件**，教会它一件它本来不会的事：怎么看照片。
插件提供一组受限领域动作（分析、偏好、全池评估、精排计划/执行、独立审计、提议与导出）。
“选出最佳人物”有固定的 v3 门禁顺序，主 Agent 不能拿旧诊断工具或本地分数绕过它。

## 安装

### 你需要先有

| | 怎么确认 | 没有的话 |
|---|---|---|
| **macOS** | — | 换不了，人脸识别用的是苹果自带的能力 |
| **Xcode 命令行工具** | `swift --version` | `xcode-select --install` |
| **Node.js** | `node --version` ≥ 22.19 | [nodejs.org](https://nodejs.org) |
| **pnpm** | `pnpm --version` | `npm install -g pnpm` |
| **一个支持图片输入与 tool call 的 AI API Key** | 见下 | 没有时只能做本地分析和配置诊断，不能声称挑出了“最好的人像” |

### 装

```bash
git clone https://github.com/tanweiping1012-source/PhotoFilterAgent.git
cd PhotoFilterAgent
PHOTO_FILTER_ALLOWED_ROOTS='/绝对路径/照片测试' \
PHOTO_FILTER_EXCLUDED_RELATIVE_PATHS='me-pick' \
./install.sh /绝对路径/deepseek-harness
```

脚本会验证 Harness `dsh-v0.1.0-rc.8`、编译本地分析引擎、装好配置、跑一遍自检。
**可以重复执行**，只补缺的部分，不会把已有的搞坏。
其他 Harness 版本会明确停止；不会静默回退到旧 profile 或旧模型路由。
`PHOTO_FILTER_EXCLUDED_RELATIVE_PATHS` 使用“每行一个、相对于照片根目录的路径”；离线验收时
必须把人工 `pick` 目录放在这里。引擎会在读取图片、生成 dataset fingerprint 和匿名 ID 之前
跳过整棵子树。普通用户没有 oracle 时保持空值，不会根据目录名自行猜测或排除。

### 在 Harness 里选择模型

Photo Curator 不固定任何视觉供应商或模型。主 Agent、全池 baseline、high 复核、
AB/BA pairwise 和独立 evaluator 都统一使用当前 DSH 会话选中的同一个
`provider/model`；凭据也完全由 Harness provider 管理。配置形态如下：

```yaml
llm-pi-ai:
  providers: { YOUR_PROVIDER: { apiKeyEnv: YOUR_PROVIDER_API_KEY } }
agent-default-model: { provider: YOUR_PROVIDER, model: YOUR_MODEL }
```

当前模型必须明确声明 `image input`，并能用 tool call 返回结构化评分。首张图片发送前，
程序先校验精确路由、JPEG/双图限制，再发一次**不含图片**的极小 tool-call 动态探针，
用来确认凭据、路由与结构化输出实际可用。该探针会产生少量 token；失败时明确阻止，
不会悄悄换到其他模型。

切换 provider、model、reasoning effort、评分协议或 rubric/prompt 会使相关 score、draft 和
audit cache 全部 fail-closed 失效，避免把不同模型的结果混用。

> **大概要花多少钱**：`evaluate_pool` 会先完成全池 low baseline；`build_selection mode=plan`
> 再给出本轮 planned high、缓存命中、待付费 high、pairwise 组数和双向调用上限。
> 实际费用以这份冻结 plan 和服务商当时单价为准，README 中的历史调用数不能替代本次预算。

### 跑

**图形界面**（推荐第一次用）：

```bash
cd /绝对路径/deepseek-harness && pnpm dsh --profile web
```

然后浏览器打开 `http://127.0.0.1:3080`，像聊天一样提要求。

> ⚠️ 这个命令会**占住终端窗口**，别关它，也别在这个窗口里再敲别的命令
> ——敲进去的字会被它当成输入吃掉。要跑别的命令请新开一个窗口（⌘N）。

新建任务时选择 **Photo Curator**，再在当前 DSH 会话里选择本轮 provider/model。
旧 `run.sh`/`photo`/`photo-web` profile 已 fail-closed 停用，因为它们不能保证 v3 全链路
使用当前会话同一模型，也绕过了新的付费计划和导出确认边界。

## 它在背后是怎么想的

### 先说一件反直觉的事

模型在这里承担**三个相互隔离的岗位**。隔离的是会话、prompt、rubric、缓存和可见状态；
它们的路由必须统一使用每位用户当前 DSH 会话选中的同一个 `provider/model`，
Photo Curator preset 本身不固定任何供应商或模型：

| 岗位 | 它能看到什么 | 它负责什么 |
|---|---|---|
| **主 Agent** | 工具返回的匿名清单、排名与状态；也会在任务文本和工具参数中看到用户授权的目录字符串 | 按 v3 门禁调用动作，不直接观看图片像素 |
| **one-shot 打分员** | 一张匿名衍生 JPEG 和固定 baseline rubric；看不到文件名、路径、排名、选择标签或用户偏好 | 给单张照片六维评分 |
| **独立审计子 Agent** | 用户授权目录、候选范围、冻结匿名 ID、K 和 seed；看不到主 Agent 的理由、偏好和 selector 分数 | 独立调用 audit v3，完整覆盖后寻找质量反例 |

主 Agent 不接收图片像素，one-shot 视觉请求也不接收文件名或路径；但这不等于路径对整个
Agent 系统不可见：主 Agent 和独立审计子 Agent 的文本上下文目前会看到用户授权的目录。

PhotoFilterAgent 自己注册五字段 `independent_evaluator`，在每次调用时从父会话最新
`request/header` 冻结 provider/model/reasoning，再创建新的隔离子 Agent；通用、可接收任意 prompt
的 subagent 工具不参与这条链路。PhotoFilterAgent 还会在审计付费调用前比较 selector 与 evaluator
的完整路由身份；不一致就失败关闭并要求重新评分，绝不静默换模型。更换模型后旧 score、draft
和 audit cache 自动失效。

看图的模型每次只看一张 baseline 图，或一对 AB/BA 比较图，也不知道主 Agent 的选择理由——
它只返回当前隔离请求要求的结构化观察，然后结束。

> **为什么要这么拆**：图片一旦进了对话历史，之后每一轮都要重发一遍。
> 打 100 次分就是 100 份图片反复在上下文里穿来穿去，又慢又贵。
> 让"打分"这个动作自己去调 AI、只交回一行数字，历史里就只剩文字。

### 第 1 步 · 本机先扫一遍（不联网、不花钱）

决策者收到你的要求，第一件事是调 `analyze_folder`。
这一步**没有任何 AI 看图**，是一个独立的本地程序在干活：

- 判断这是**人物照**还是**风景照**
- 把**看起来几乎一样**的照片归成一组（同一个场景连拍了一串）
- 算清晰度、明暗层次、有没有过曝
- 检测人脸，并判断**眼睛是睁着还是闭着**
- 按安装时明确配置的相对路径隔离验收 oracle；被隔离子树不会进入候选、fingerprint 或匿名 ID

> 这四件事里，苹果系统只帮忙做了一部分，剩下的是这个项目自己写的算法。
> 具体谁做了什么 → [苹果帮了多少忙，我们自己写了多少](#苹果帮了多少忙我们自己写了多少)

473 张，**14 秒**，零成本。

交给决策者的是一张**纯文字表**，长这样：

```
p001 风景 清晰79 宽容100 过曝18 +9878s
p289 人物 清晰47 宽容95 过曝5 连拍F25 脸质量62 眼睛睁30 +22360s
p296 人物 清晰45 宽容99 过曝10 连拍F26 脸质量41 本地提示:可能闭眼 +22554s
```

领域工具返回的候选行**没有真实文件名和逐图路径**——只有 `p001` 这样的编号，
和"距第一张多少秒"。目录参数本身仍会出现在主/子 Agent 的授权文本中；真实文件名到编号的
对照表保留在本机状态中，不进入单张视觉 one-shot。

#### 关于“可能闭眼”的本地提示

这是本机免费产生的诊断信号，不是最终资格判定。闭眼可能是眨眼失误，也可能是有意的神态；
v3 rubric 明确规定它**不能自动硬淘汰**。只有无法评估、没有有意人物主体、主要人物不可解释、
灾难性拍摄失败四类情况可以触发资格门槛。闭眼、背影、剪影、遮挡、运动模糊或非常规表情
应结合可观察意图影响“人物瞬间”等维度；意图无法判断时进入 `needs_review`。

### 第 2 步 · 锁定结构化偏好

主 Agent 调用 `set_preferences`。没有偏好时使用冻结 baseline；用户可以在白名单内调整表情、
视线、景别、光线、氛围、多样性和连拍保留策略。偏好只产生最多 ±4 分的第二列，不改写
baseline，也不能恢复资格不合格的照片。省略 `diversity` 表示继承 baseline 的 balanced 强度 1；
显式 0 才是关闭。

### 第 3 步 · 全池 low baseline

`evaluate_pool detail=low` 评估**全部人物候选**，包括旧候选视图里折叠的连拍成员。每张照片
按固定六维 rubric 独立评分，总分由宿主按 18/22/18/16/16/10 重算。普通中断在后续新 turn
以相同参数只补 missing；不能把整池改成 high。401/403/429、鉴权、额度或路由能力失败会返回
`BLOCKED + next_action=fix_model_route`，当前 turn 禁止自动重试或轮询 status。没有可用 Key 或视觉
路由时，这一步不会完成，因此只能报告本地分析/配置诊断，不能声称已经挑出“最好的人像”。

### 第 4 步 · 先 plan，再执行精排

`build_selection mode=plan` 冻结高成本预算，展示 planned high、缓存命中、待付费 high、
预计 pairwise 组数与双向调用上限。费用以本次 plan 和供应商价格为准。获得付费授权后，
`build_selection mode=run` 才在 hard cap 内复核高分、同族 challenger 和切线候选，并自动执行
A/B、B/A 两个顺序的 pairwise。中断后用同一 plan 重试，只补剩余项。最后产出恰好 K 张的
冻结 draft；主 Agent 不能手工改名单。

### 第 5 步 · 独立 evaluator 执行 audit v3

主 Agent 只能把授权目录、候选范围、冻结匿名 ID、K 和 seed 交给专用
`independent_evaluator` 子 Agent；不能传选择理由、偏好、selector 分数、排名或中间推理。
子 Agent 独占 `audit_selection` 且每次恰好调用一次：先 high 盲评全部入选项，再 low 覆盖其余候选，按冻结计划提升
可能胜出的挑战者并做双向 pairwise。`INCOMPLETE` 只表示尚未覆盖完成，必须保持五项输入不变
在后续新 turn 继续补跑；同一主 Agent turn 最多启动一次 evaluator。若返回 `BLOCKED`、
`next_action=fix_model_route` 或 `circuit_breaker`，父子 Agent 都必须立即停止；同一失败路由再次进入
审计只读取已保存报告，provider 调用数为 0。只有完整覆盖后的 `PASS` 才能进入下一步，`FAIL`
则退回重建名单。

### 第 6 步 · propose 代码门禁

`propose` 只接受 `build_selection` 冻结的 exact-K 原名单，并验证 dataset、scope、rubric/prompt、
provider/model、preference、selection hash 与 audit v3 PASS 全部一致。主 Agent、旧版 `inspect` /
`compare` / `resolve_family` 和纯本地兜底都不能绕过这条门禁。
若本轮配置了 oracle 排除子树，`propose` 还会通过本地引擎流式计算 exact-K 入选原图的
SHA-256，生成不可覆盖的 content-addressed receipt。Receipt 绑定 dataset、scope、selection hash、
audit PASS、实际模型路由、rubric/prompt、排除策略和匿名 ID↔内容哈希；这一步仍不读取 oracle，
也不需要导出或复制照片。之后独立进程只有完整验证 receipt，且确认 oracle 的 realpath 恰好是
receipt 声明的排除子树，才允许计算重合率。

### 旧第 2 步 · 几乎一样的照片，先比不打分

上一步找出的"看起来几乎一样"的那些组，**默认是折叠的**——
每组只有一张露在候选名单里，其余的根本不参与竞争。
决策者想动它们，必须明确地调"比较"这个动作。

**为什么要强制？** 因为早期版本里折叠是可选的，结果 AI **一次比较都没调**，
78 组连拍全被无视、每张单独打分。而连拍恰恰是唯一能可靠判出
"哪张睁着眼"的地方——三张里两张闭眼，摆一起一眼就看出来，
分开打分则会各自拿到 63、64、63。

**能绕过的约束等于没有约束**，所以改成默认生效。

比较是这么做的：本地把这几张各生成一张 **512 像素的小图**，
一次性发给 AI 问"哪张最好"，只把一行结论收回来：

> 第 3 组的胜者是 `p011`：另外两张一个眨眼，一个手挡住下巴

**为什么用比较而不是打分**：同一组照片的差别在眼神、表情、手的位置。
绝对打分给不出这种区分度，摆在一起比就分得出。

**为什么只用 512 像素**：比较只需要判断"谁更好"，不需要看清细节。这是最便宜的一档。

比完之后同组其余照片退出竞争。全库实测：**473 张缩到 86 张**，全程零成本。

> **一个没修干净的坑**
>
> 折叠时"留哪一张当代表"，最早的版本是按编号顺序留第一张——
> 等于随机指定一张当门面。全库跑下来，39 个组里有 **2 个组的门面本身就是闭眼照**。
>
> 也就是说：那个"挑出来全是闭眼照"的毛病，换了一层又冒出来了，
> 而且更糟——AI 连给它打分的机会都没有，它直接以代表身份进了名单。
>
> 现在改成按本机已经算出的免费事实排：**先排除闭眼，再看人脸质量，再看清晰度**。
> 改完之后闭眼代表 **2 → 0**，候选池大小不变，一分钱没多花。

### 旧第 3 步 · 粗排：全部用小图快速过一遍

剩下的 86 张，每张生成一张 512 像素小图发去打分。
**4 张同时进行**——这些请求互不相干，一张张排队等于把等待时间叠加起来。
实测 8 张：串行 37.2 秒，并发 **11.8 秒**。

**人物照和风景照用两套不同的打分标准。**
人物那套把**闭眼、遮挡、脸失焦、表情失真**明确列为硬伤，
命中任意一条就必须打低分，并且明确禁止用「自然」「不摆拍」「有情绪」「闭目沉思」
这类理由往上抬分。风景那套不需要这些。

打分员只给五个维度的分，**总分由本地按权重算**——整数运算，换台电脑结果一样。

收回来的仍然只是文字：

```
p001  总分 58 [瞬55 构62 主58 光65 叙50]  雪林小径氛围安静，构图平淡
```

**为什么这一步全用便宜档**：这一步的目的是**淘汰**，不是排名次。
86 张里一多半会在这里出局，为它们花高清的钱是浪费。

---

### 旧第 4 步 · 停下来算一笔账：还值不值得继续花钱

决策者调"看看现在什么情况"，拿到的是一份**当场算出来的处境摘要**：

```
【人物】目标 2 · 候选 13 · 已看 13
  当前前 2: p029(66) p026(63)
  第 2 名和第 3 名差 6 分   → 稳
【风景】目标 2 · 候选 8 · 已看 8
  当前前 2: p005(66) p008(65)
  第 2 名和第 3 名差 1 分   → ⚠ 不稳，值得再看
```

关键就是那个**分差**——第 N 名和第 N+1 名之间差多少（N 就是你要留几张）。
它直接回答"还要不要继续花钱"：

- **差 6 分** → 稳。再怎么看名次也不会变，**别花这个钱**
- **差 1 分** → 不稳。这个名次基本是噪声决定的，**值得放大看**

---

### 旧第 5 步 · 精排：只有分差不稳的那几张，才配用高清

对着分界线上下那几张，重新生成 **1536 像素**的大图再看一遍——
这个尺寸能看清表情、纹理、对焦到底有没有落在眼睛上。

这一步经常翻盘：

> `p014` 粗排排第二（64 分），高清看完跌到 51——
> 典型的"到此一游"纪念照，小图看着还行，放大就露馅了

同一张照片如果之前已经用同等或更高的清晰度看过，**直接返回上次的结果，不重复计费**。

**尺寸策略一句话**：

| 档位 | 用在哪 | 为什么 |
|---|---|---|
| **512 像素** | 比较 · 全池粗排 | 比较只要相对判断；粗排只要淘汰 |
| **1536 像素** | 只有分差不稳的那几张 | 名次被噪声决定时，才值得看清表情和对焦 |

**便宜的钱花在"排除"，贵的钱花在"决定"。**

---

### 旧第 6 步 · 交名单，代码来把关

AI 提交最终名单时，**由代码做五项检查，不靠它自觉**：

1. 每张都还在候选名单里
2. 没超过你要的数量
3. 同一组几乎一样的照片，不能选出两张
4. **每张都必须真的被看过**——防止它推荐一张从没打开过的照片
5. 每张都得有理由

不通过就把**具体哪里错了**告诉它，让它改了再提。

</details>

### 第 7 步 · 你点头，才复制

编号在这一步才映射回真实文件名。
导出采用两阶段确认：第一次只冻结名单、目标目录并返回一次性码，必须由用户在一条新消息中精确确认后才复制。
导出**只做复制**：原图不移动、不删除、不改名、不写回；目标已有同名文件时拒绝覆盖。

## 你的照片会被传到哪里去

这是最该问的问题，直说：

**会传出去的**：本地程序生成的**缩小过、去掉全部元数据**的 JPEG（512 / 1024 / 1536 像素），
发给 AI 服务商用于打分。

**不会进入视觉 one-shot 的**：原图、文件名、文件路径、GPS 位置、拍摄时间。主 Agent 和
独立审计子 Agent 的文字上下文仍会看到用户授权的目录字符串，以便调用受限领域工具；这和
“视觉模型只收到匿名衍生 JPEG”是两个不同边界。

这不靠 AI 自觉，靠**把工具拿掉**：配置里关掉了 harness 自带的全部通用文件读写和
命令行工具（`tool-bash` / `tool-fs` / `tool-fs-search` / `skill-filesystem` /
`str-replace-editor` / `tool-web`）。它想绕也没有路。

> **为什么要关**：实测记录里，AI 真的尝试过用通用工具**直接读原图**。
> 那会把全分辨率、带 EXIF 和 GPS 的原图整个送进对话——
> 绕过所有的匿名化、缩小和元数据剥离。
>
> 关掉之后这条路就没了。

**图片像素不进入主 Agent 的对话历史**。领域工具会在 Harness attachment service 内
保存匿名衍生 JPEG 的耐久引用，通过同一 provider/model 的隔离 one-shot 只发 rubric 和
1–2 张图，然后只把紧凑分数交回主循环。因此后续对话不会反复重发照片。

| | |

## 它做不好什么

这一节不是免责声明，是实测发现的真问题：

1. **有些策略仍然是任务提示里教的，不是它自己想出来的。**
   命令行版把步骤写进了任务文本。虽然闭眼修复后那次是不给提示跑通的
   （说明把规则写进工具说明比写进任务文本管用），但**只验证过这一次**。

2. **折叠很激进，而且它挡住的主要是人物照。**
   全库 307 张人物照被 14 个组吃掉了 302 张，折叠后候选里**只剩 17 张人物**。
   一个 49 张的"组"已经不叫连拍了，那是**整段场景**——这段里最好的那张
   未必就是被留下的代表。而"比较"一次最多只收 4 张，49 张的组没法一次比完。

3. **除了折叠，没有别的省钱手段。**
   折叠后剩下的 86 张，粗排阶段是**全部**打一遍分。
   前身 App 里有个"本地规则先挑 48 张"的守门人，被拿掉了，没有等价替代。

4. **高风险操作的确认闭环已经补上，但还不是原生弹窗。**
   导出现在必须经过“冻结名单与目标 → 返回一次性码 → 用户在新消息中精确确认”两阶段门禁，
   并默认拒绝覆盖同名文件。交互仍是聊天确认，不是系统级原生确认框。

5. **选片质量只在小样本上量过**，不构成统计结论。
   另外有个**负面结果**要说清楚：**本地那些技术指标和人的口味基本无关**——
   按清晰度/宽容度/过曝排出来的前 6 张，和用户人工精选的 20 张**重合 0 张**，
   比随机还低。人工精选散落在系统排名的第 20 到第 302 名之间。
   你选的是表情、是瞬间，本地分析器看不见。所以这些指标只用来**描述底子**，不用来定名次。

6. **历史全量 473 张的完整视觉筛选没跑过**，旧验证做到 50 张取样；当前 v3 的质量结论
   必须单独报告完整执行范围、plan、audit 覆盖和 oracle 指标，不能沿用这些旧数字。

7. **DeepSeek Harness 目前是 v0.1 开发者预览版**，官方明确会有破坏性改动。
   本仓库当前只验收并 fail-closed 锚定 `dsh-v0.1.0-rc.8`；换版本必须重新适配和验收，安装器不会回退旧 profile。

## 苹果帮了多少忙，我们自己写了多少

有个很容易产生的误解：以为"判断人物照还是风景照"是调一个苹果的 API 就搞定的事。

**不是。苹果没有这个 API。**

### 苹果的 Vision 是传感器，不是判断者

Vision 是 macOS 自带的图像识别框架。它只吐**原始事实**，一个判断都不下：

| 我们问 Vision | 它只回答 |
|---|---|
| 有脸吗 | 有一张，框在这个位置，拍摄质量 0.53 |
| 有人吗 | 有个人体，框在这，置信度 0.71 |
| 人在哪些像素上 | 这是人物区域的掩码 |
| 有几个人 | 这几团像素分别属于不同的人 |
| 视线会落在哪 | 这是画面的视觉焦点分布图 |
| 眼睛在哪 | 这是眼睛轮廓的一串坐标点 |

注意它**一次都没说"这是人像照"**。它说的全是"这里有个东西"。

### 真正难的问题，Vision 一个都答不了

- 一个人站在冰川前，只占画面 2% ——**这算人物照还是风景照？**
- 三个游客路过入了镜——**这是合影还是风景照？**
- 眼睛轮廓的坐标拿到了——**所以眼睛到底闭没闭？**
- 这两张画面很像——**是同一个瞬间连拍的，还是不同时候拍了同一个地方？**
- 这张看起来不太锐——**是拍糊了，还是这个场景本来细节就少（干净的雪山、纯净的海面）？**

这些全是**自己写的算法**在回答。

### 代码上是什么比例

```
本地引擎总计 2534 行
├─ 完全不碰苹果框架   1624 行   64%
└─ 会调用 Vision 的     910 行   35%
     └─ 其中真正是 Vision API 调用的，只有十几行
```

最典型的是分类那个文件：**589 行代码里，出现苹果 API 的只有 14 行**，
剩下 575 行全是自己写的判定规则，带 15 个手工标定的门槛值：

```swift
脸小于画面 0.8%           → 不算人像
脸得在画面里足够占主导     → 门槛 0.42
超过 3 个人               → 不算"风景配人"
人得占据视觉焦点一半以上   → 门槛 0.50
```

**那个 99.6% 的分类准确率，是这层规则的成绩，不是 Vision 的成绩。**

### 完全自己写、一行苹果 AI 都没用的部分

| 做什么 | 怎么做的 |
|---|---|
| **找出"几乎一样"的照片** | 把每张压成 8×8 的灰度指纹，比对有多少格不同 |
| **把它们聚成组** | 低对比度的画面**不自动分组**——否则一堆过曝的白、纯色的天会被误当成同一张 |
| **算清晰度** | 见下，这个最有讲究 |
| **没有 API Key 时的本地诊断** | 可分析分类、家族与技术信号；不能通过 v3 视觉评分与审计，因此不能声称挑出了最好的人像 |

#### 清晰度为什么不能直接算

这里三个决定都是踩过坑才定下来的：

1. **只统计最强的那一小撮边缘**，不用整张图的方差。
   因为大片天空、纯色背景会把全局统计**稀释掉**；
   而用固定分位（比如取前 10%）在边缘稀疏的画面里会直接落进平坦区域，读数变成 0。

2. **除以画面反差**做归一化。
   否则阴天的低反差场景和晴天的高反差场景根本没法放在一起比。

3. **只在同一组相似照片内部比较**，不跟全库比。
   否则一张干净利落的雪山风景，会因为"细节本来就少"被误判成拍糊了。

### 闭眼判定也是自己写的

苹果**没有**"检测眨眼"这个功能。它只给眼睛轮廓的坐标点。

从坐标到结论这一步是自己算的：量眼睛轮廓的**高度除以宽度**——
睁开时这个比值大，闭上时明显小。

阈值 **0.22** 是拿真实照片标出来的：闭眼的三张量出 0.15 / 0.12 / 0.09，
睁眼的三张是 0.31 / 0.48 / 0.48，中间空档很宽，取中央最稳。

（早期版本取 0.11，结果 0.15 和 0.12 那两张明明闭着的被判成睁开了。）

### 一句话

**苹果 Vision 负责"看见"，所有的"所以呢"都是自己写的。**

而准确率恰好就取决于后面那半。

## 它的前身

这个项目改写自 [PhotoFilter](https://github.com/tanweiping1012-source/PhotoFilter)，
一个 macOS 原生 App。那个是**流水线**，这个是 **agent**：

| | PhotoFilter（App） | 这个 agent |
|---|---|---|
| 谁决定看哪些照片 | 320 行写死的规则挑出 48 张 | AI 看着清单自己决定 |
| 每张看多细 | 全部一个档，第 1 名和第 48 名花一样的钱 | 按需要，只在关键处花贵的 |
| 连拍组留哪张 | **谁最锐利谁赢**——纯技术指标 | **真的比一次**，让 AI 看着选 |
| 流程形态 | `for` 循环，计划在联网前就定死了 | 下一步取决于上一步看到了什么 |
| AI 知道目标吗 | 不知道，只收到"给这张打 5 个分" | 知道要留几张，也看得见分差 |

最实质的差别是**连拍组留哪张**。App 用"谁最锐利"糊弄过去了，
但同一组照片的差别根本不在清晰度，在一个眼神、一只手的位置。

App 那套本地分析引擎原样搬了过来，但在这里**降级成了免费工具**——
不再决定谁能进候选池，只负责回答"有哪些照片、各自什么底子"。
