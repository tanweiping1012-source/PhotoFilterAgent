# rubric 怎么进系统

> **这份文档被推翻重写过一次。** 第一版的结论是「只有三条该进提示词,
> 其余都该进代码」,理由是「可测量的判据本地做得更准更便宜」。
> 那个结论有两个问题,都是用户指出来的:
>
> 1. **「进代码」实际写成了「写死」** —— 那会把一个人的审美变成所有人的审美
> 2. **支撑它的证据不成立** —— 见下面「一个被推翻的论证」
>
> 旧版见 git 历史(`dad9dcc`)。保留是因为它错在哪比它说了什么更有用。

## 原则

**rubric 是用户的,不是引擎的。整份都归用户改,整份都进模型。**

编译只是**加速**,不是筛选:能被引擎认出来的条目额外下沉到阶段 1,
认不出来的照样原样进提示词、照样生效,只是阶段 1 帮不上忙。
**没有任何规则会因为编译不了就失效。**

## 两条轴必须分开

|  | 谁来定 |
|---|---|
| 规则由谁**表达** | **永远是用户。** 这一条没有例外 |
| 规则由谁**执行** | 代码或模型 —— 只由成本决定,不由「谁更准」决定 |

「用户可调」不等于「必须由模型执行」。一条规则可以是用户写的、随时能改的,
同时由本地确定性代码执行 —— 只要**参数来自那份 rubric,而不是硬编码在引擎里**。

## 数据流

```
用户的 rubric（一份文本，随便改，唯一真源）
  │
  ├─→ 阶段2 组内比较：**原样全文进提示词**
  │      改一个字立刻生效，不需要改代码
  │      这里每组只比 n-1 局，成本可承受
  │
  └─→ 阶段1 过滤废片：能编译的条目编译成门限
         「闭眼一票否决」→ 闭眼门 on，阈值取自 rubric
         「脸没对上焦」  → 对焦门 on（本地缺口，见下）
         编译不了的      → 阶段1 不管，留给阶段2 的模型
```

反过来也成立:用户把「闭眼一票否决」从 rubric 里删掉,闭眼门就自动关掉。
**想要闭眼的抓拍照,删一行字就行,不用碰代码。**

现在的 `config.py:182  block_closed_eyes: bool = True` 是个写死的默认值,
这正是该改的地方 —— 它应该读 rubric,而不是自己有主张。

## 为什么阶段 1 必须本地:成本,而不是能力

三个阶段的经济学完全不同:

```
阶段1 过滤废片    跑遍全部 N 张      5000 张的旅行 → 至少 5000 次调用
阶段2 组内比较    只跑组内的 n-1 局   133 张 → 55 局 = 110 次调用
阶段3 全局配额    纯本地
```

阶段 2 交给模型可承受,这也是现在的设计。阶段 1 不行 ——
一次旅行 5000 张,光「有没有闭眼」就要 5000 次调用,而本地 1.5 秒能算完。

**这是算术,跟模型强弱无关。** 下面那条跟模型强弱有关的论证,已经不成立了。

## 一个被推翻的论证(留档)

第一版这份文档用了两个证据反对「全部交给模型」:

**证据一(仍然成立):** 标注者对不同判据的重测稳定性差 4 倍 ——
对焦 / 低头 / 眯眼 / 抿嘴 都是 100%,而眼神 60%、瞪眼和曝光和五官各 25%。
可测量的物理事实稳,主观审美不稳。
→ 这个结论没被推翻,但它**不能推出「所以要写死」**,只能推出
「主观维度上真值本身抖,任何一致性数字的上限都被它压着」。

**证据二(不成立):** 「v3 让模型判断,997 次调用交付 3/20,已经证明模型不行。」

复查发现这是混淆的:

```
v3 的规格（512px 整幅）   人脸中位数 45px · 25分位 34px · 最小 21px
                          <96px 的占比 100%   ← 96px 是本项目自己定的「能看清脸」门槛
v4 现在发的人脸特写                  448px    ← 线性分辨率 10 倍
```

在 45 像素的脸上判「眼神有没有神」,评分当然抖。那测的是
**「看不见时的猜测方差」**,不是「模型判不准」。

**所以:「模型在能看清脸 + 规则清楚的条件下能做到什么」,
这个项目至今没有干净地测过一次。** 这正是 AB 实验要产出的东西。

## 本地缺口:对焦

`EngineFacts` 的字段是 `closed_eyes / face_quality / big_face /
eye_openness / face_area / face_box` —— **没有任何清晰度字段**;
`rank.py:96` 的资格门也只有 `blocked = facts.closed_eyes & set(names)`。

Swift 侧 `TechnicalQualityAnalyzer` 算了 `sharpness`,但那是**整张图**的,
而 `eligibility.py` 自己的注释就写着「整张图锐不锐」和「脸清不清楚」是两件事。

对焦是标注者最可复现的规则(重测 10/10 = 100%,单独淘汰过 2 个整组),
而且本地可算(`face_box` 已有,框内算一次拉普拉斯方差)。
按上面的原则,它应该是**rubric 里的一条 + 一个可编译的门限**,
而不是写死的引擎行为。

## 一个必须说清楚的代价

阶段 1 只执行「编译得出来」的那部分。对审美与默认 rubric 差别很大的用户,
**阶段 1 会偏弱,主要靠阶段 2 兜**。这是诚实的退化,不是 bug ——
但要让用户知道,而不是让他以为阶段 1 也在按他的规则筛。
