# v4.6 · 缩略图按 EXIF 方向摆正

**一句话**：9% 的照片一直是横躺的，而且完全无声。

## 怎么发现的

用户要求「给我一张照片的例子看看，清不清楚」—— 想确认发给视觉模型的
448px 人脸够不够清楚。生成出来一看，**整幅小图里的人是躺着的**。

我此前把这条链路跑过几十次，从没打开看过其中任何一张。

## 根因

相机竖着拍时，像素通常仍按**横向**存储，靠 EXIF 的方向标记（tag 274）
告诉看图软件转多少度。

`scan.py` 的 `build_cache` 从来没读过这个标记：

```
原图像素        7728x5152（横向存储）
EXIF 方向标记    8 = 需逆时针转 90°
实际应该是        5152x7728（竖幅）
```

而缩略图缓存同时喂给了**三处**：

- CLIP 图像特征 → 分组依据
- pyiqa 质量分（topiq_nr-face / laion_aes）→ 排序依据
- 发给视觉模型的整幅小图

测试集 309 张里有 **28 张（9%）** 受影响。**不报错，只是所有下游结果
都基于一张躺倒的图。**

## 不受影响的部分

Swift 引擎那一侧一直是对的 —— 它解码时带
`kCGImageSourceCreateThumbnailWithTransform: true`，Vision 拿到的是摆正的图。

所以闭眼资格门不受影响：拦下的张数修前修后都是 52。人脸裁切也是对的
（v4.5 已单独处理过方向）。

## 缓存失效必须一起做

缓存键只由**原图路径**决定，而修 bug 时原图一个字节没变 ——
不换键的话，修好的代码会继续读旧的横躺缓存，而且同样无声。

```
缩略图键     加 -o1 后缀
embedding    emb-{fp}-ViT-L14.npz → emb-{fp}-ViT-L14-o1.npz
质量分       quality-v2-{fp}.json → quality-v3-{fp}.json
```

## 一个自己造的坑

第一次改完，预览**还是横的**。

因为 `cli.py` 的 `preview` 子命令**自己复制了一份缓存键算法**，
我只改了 `scan.py` 那份。于是它继续读旧缓存，发给模型的图还是转了 90° 的。

已提取成单一函数 `scan.thumb_key()`，并加测试禁止 `cli.py` 再自己算键。

## 评测结果：交付没有变好

如实记录：

| 挑几张 | 修之前 | 修之后 |
| --- | --- | --- |
| 10 | 3/20（p=0.021） | **2/20（p=0.131）** |
| 20 | 6/20 | 6/20 |
| 50 | 10/20 | 10/20 |
| 场景组数 | 128 | 127 |

28 张转向照片里有 2 张是用户精选。K=10 掉一张属于重算分数后的连带波动，
在 n=20 金标、K=10 这个尺度上属于噪声范围。

**这个修复的正当性不在指标，而在于发给模型的图本来就是错的。**
一张躺倒的照片，再高清也没用。

## 一个推论

v3 那 997 次付费调用用的是**同一套缩略图缓存**。

也就是说：那批调用里同样有约 9% 的图是转了 90° 发出去的。
「AUC 0.497 = 随机」这个结论现在多了一个可能的解释 ——
虽然远不足以推翻它（噪声 σ=7.28 > 信号 σ=6.72 才是主因），
但它提醒一件事：**在怀疑模型之前，先打开看一眼你到底发了什么给它。**

## 教训

这一整节的价值不在代码，在于它暴露了一类**监控和日志都看不见**的错误：

- 日志显示「生成 1 张 512px 预览，36KB，EXIF 字段 0」—— 全部正常
- 单元测试通过 —— 因为没有一条测试打开过图片
- 指标没有异常 —— 因为 91% 的照片方向本来就是正的

**只有真的把图打开看，才看得见。**
