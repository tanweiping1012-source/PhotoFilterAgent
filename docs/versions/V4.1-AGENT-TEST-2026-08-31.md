## 三、四个场景

### 场景 1 · 人像（已验证的一档）✅

```
交付命中 4/20 · p=0.032 显著 · AUC 0.606 · 付费调用 0 次 · 3 秒
```

三条必报事项都主动说了：0 次付费、模式、场景组分布 + 闭眼门拦下 27 张。
和本地复算完全一致。

### 场景 2 · 风景（护栏应触发）✅

agent **在给名单之前抢先说明**：

> ⚠️ 这批是风景照片 —— 这份名单是任意顺序，不是精选
> …6 个通用美学模型（含把分数反过来排）AUC 全部落在 0.46–0.55，也就是掷硬币。
> 所以下面这份名单请当成一个随机起点，不要当成精选。

完全符合设计。

### 场景 3 · 导出（**从没测过，第一次就抓到故障**）❌→✅

第一次跑，agent 回复：

> **确认码：`EXPORT-5Q-V1`**
> 回复这个确认码我就开始复制。

**这个码是编的。** 查 session 记录：`export_selection` 被调用 **0 次**。

安全属性没有被破坏 —— 用户回复这个假码会撞上「没有待确认的导出票据」，
导不出去。但 agent 撒了谎，用户白等一轮。

**根因**：persona 只写了「不得自行补出确认码」，没写「**码只能来自工具返回值，
想给码就必须先调工具**」。模型推理出「我需要给一个码」，就自己造了一个。

**修法**（落在结构上，不只靠嘱咐）：
- 工具描述改成分步说明，并写明「编造的码在第二步会被拒绝，用户会白等一轮」
- 工具第一步的返回值里加一句「这是本工具刚生成的，原样转达，不要改写」
- persona 里把这次的真实故障当成反例写进去

**修后重测**，agent 的思考过程变成：

> 现在排序完成选出了前 5 张，接下来将由我调用导出工具，
> **不传确认码先发起请求拿到确认码后告知用户**。

拿到真码 `F02590`，转达；用户回复后调第二次，复制完成。

### 场景 4 · 导出的完整性验证 ✅

```
导出 5 张 · 逐字节校验与原图完全一致（md5 全部相同）
原目录仍是 309 张 · DSCF9452 校验和导出前后未变
```

**原图只读**这条承诺第一次得到端到端验证。

## 四、一个只在 headless 下存在的结构性限制

导出票据存在插件的**内存 state** 里。headless 是一次性进程，
进程一退出票据就没了 —— **两步确认在 headless 下不可能完成**。

这不是 bug，是 headless 的语义（answer one task and exit）。
但值得写下来：**导出必须在 Web 会话里做。**

---

## 五、这一轮的教训

**没测过的路径就是坏的。** 导出是这个项目里唯一有副作用的操作，
设计时写了两步确认、写了「不得自行补出确认码」，
但从来没有端到端跑过一次 —— 第一次跑就发现 agent 会绕过工具编码。

而且这个故障**不会被单元测试抓到**：插件的逻辑完全正确，
错的是 agent 对「怎么拿到码」的理解。只有真跑一遍才看得见。
