# 人像质量：把本地信号榨干之后，天花板在哪

> 2026-08-30。这一轮只做一件事：**把人像这条线做到本地信号的尽头**，
> 然后如实说明剩下的差距需要什么才能补。

---

## 一、诚实的成绩

```
交付前 20 命中     3–4/20（五次 Vision 扫描：4, 4, 3, 3, 4，均值 3.6）
超几何 p 值        0.03 ~ 0.13，五次里三次过 0.05 线
AUC               0.704 ~ 0.744
随机期望           1.29/20
付费调用           0
```

**我之前报的「4/20，p=0.032 显著」是抽样分布的好的那一端。**
真实情况是 3–4/20，大约六成运行能过显著线。波动来源是
Apple Vision 的人脸质量本身不确定（同一批扫两遍，106/280 张分数差 1–5 分），
而前 20 名这条切线对 ±1 分极度敏感。缓存把结果锁定成确定的一次，
但锁定的是哪一次是随机的。

## 二、把所有本地特征逐个量了一遍

| 特征 | AUC | 说明 |
|---|---:|---|

金标中位数 vs 非金标：人脸质量 **51 vs 38**；全局清晰度 46.5 vs 47.0（几乎相同）。

## 三、试过但没用的（全部记录在案）

### ① 「脸够大」不是信号

假设：近景人像更可能被选。实测 —— 92 张大脸照里有 **6 张金标，正好等于随机期望**
（富集 1.0 倍，p=0.58）。用户近景和环境人像都选。

### ② 所有融合都让交付变差 —— 这是第四次

| 打分方式 | AUC | 交付 |
|---|---:|---:|
| **face_quality 单独** | 0.716 | **5/20** ✅ |
| + 睁眼 0.5/0.5 | 0.730 | 3/20 |
| + 睁眼 0.7/0.3 | 0.729 | 4/20 |
| × 睁眼（乘法） | 0.730 | 3/20 |
| + topiq 人脸 0.5/0.5 | 0.680 | 4/20 |
| + laion 0.7/0.3 | 0.712 | 3/20 |
| 三者等权 | 0.702 | 4/20 |

**每一种组合都是 AUC 升、交付降。** 前三次分别是：
laion+topiq 融合、个人口味探针融合、探针+vision_face 融合。
四次独立实验指向同一个结论：**在这个任务上，融合改善中段排序、稀释头部。**

### ③ 多次扫描取平均：更差

5 次平均 AUC 0.702、交付 3/20，比大多数单次还差。

### ④ 无脸照片排最后：AUC 涨了，交付没动

AUC 0.723 → 0.744，但五次扫描的交付完全相同（4,4,3,3,4）——
那 30 张本来就进不了前 20。**这是正确性改进，不是效果改进**，已在代码里标注。

## 四、同组上限 2 是对的，而且有机制解释

|---:|---:|
| 1 | 4/20 |
| **2** | **5/20** |

成对落在同一场景组（F7、F13、F17、F31、F99 各 2 张），没有任何一组有 3 张。

## 五、天花板在哪，以及为什么

20 张金标在当前排序下的名次：

```
1, 9, 13, 20, 21, 30, 33, 64, 76, 79, 80, 98, 105, 106, 108, 139, 172, 205, 216, 236
中位 80/309 · 前 20 内 4 张 · 前 50 内 7 张 · 前 100 内 12 张
```

**八张金标排在 139 名之后。任何对这个信号的重排都够不着它们。**

组内排序的诊断更直接：17 张金标落在多成员场景组里，
其中只有 11 张排在组内前 2 —— **命中率 65%，随机基线 47%。**

大组里第二张金标常排在第 5、6、8、14 位：

```
F7  (7张)   ·★··★··
F13 (10张)  ★····★····
F17 (15张)  ··★··········★·
F31 (14张)  ★······★······
```

**这正是「同一个瞬间的连拍里哪张更好」这个问题**，而 Apple 的人脸质量
测的是拍摄技术质量，看不见表情、眼神、互动。

## 五点五、又一轮：给一个已经不存在的问题建了工具

接着往下调，先建了**组内成对比较**工具（复用 v3 的 vision transport，
AB/BA 双向问，512px 无元数据小图，模型路由继承会话）。依据是上面第五节
「组内排序命中率 65%」这个诊断。

**建完才发现那个诊断是基于修 bug 之前的分组。** 分组与打分解耦之后：

- 组内排序命中率 65% → **75%**
- 16 张漏掉的金标里，**只有 1 张**是被同组上限挡的

```
13 张  分数太低（60 名开外）      ← 真正的瓶颈
 2 张  21–60 名，差一点没进前20
 1 张  被同组上限挡掉            ← 成对比较只针对这一张
```

实测跑了 3 对（6 次调用），**全部平局，而且全都是 AB/BA 正反答案不一致** ——
模型在这些边界对上没有可靠偏好。工具留着（它是对的，且用户可主动调用），
但它解决的不是主要矛盾。

> 教训：**修完一个 bug 要重新做诊断。** 我拿着旧诊断建了一个正确的工具，
> 只是它对应的问题已经被别的修复消掉了大半。

## 五点七五、真正的瓶颈：Apple Vision 对小脸系统性低估

查那 13 张漏掉的金标，模式非常干净：

```
漏掉的 13 张里「脸大到能测眼睛」的：1/13
命中的  7 张里「脸大到能测眼睛」的：5/7
```

**漏掉的全是环境人像（人小景大），命中的全是人物特写。**

因为 Apple 的人脸质量分是在**人脸裁剪区**上算的，脸小意味着像素少、更难评估：

```
大脸组（脸 ≥0.8% 画面）   92 张   脸质量中位 56
小脸组                   217 张   脸质量中位 33     ← 系统性低 23 分
```

而用户两种都选（金标 6 大脸 / 14 小脸），所以排序器**系统性漏掉环境人像那一半**。

### 修它 —— 但它是个精度/召回权衡

按人脸大小分层（各组内部各算百分位）后，13 张小脸金标**全部上升**
（−12 到 −48 名），中位名次 80 → 61。但跨 5 次 Vision 扫描一致：

|  | K=20 均值 | 过显著线 | K=50 均值 | AUC |
|---|---:|---:|---:|---:|
| 现状（平铺） | **3.6** | **3/5** | 4.8 | 0.73–0.74 |
| 分层 | 3.2 | 1/5 | **9.4** | **0.77–0.80** |

平铺排序把少数几张对的**挤在最顶端**（金标名次 1、9、13、20）；
分层把正确性**摊得更均匀**，但顶端更少。

端到端实测（新的一次 Vision 扫描）：

```
--target 20              3/20   p=0.130     AUC 0.729
--target 20 --stratify   3/20   p=0.130     AUC 0.779
--target 50              5/20   p=0.207     AUC 0.729
--target 50 --stratify   8/20   p=0.0073 ✅  AUC 0.779
```

**产品默认要 20 张，所以默认关**（`stratify_by_face_size: bool = False`）。
要挑 50 张以上就该打开 —— 那时它接近两倍好。

> 这是第五次遇到「AUC 升、交付降」。但这次不一样：前四次是融合稀释头部，
> 这次是**修好了一个真实偏差，而增益恰好落在 K=20 这条线的下方**。
> 换个 K 就翻过来了。

## 五点九、最后一个反转：我把默认值调坏了

上面第五点七五做完之后，把人像这条线的**完整轨迹**重算了一遍
（每一档都跨 5 次 Vision 扫描），结果推翻了我自己的头条结论：

| 档位 | 交付 K=20 | 均值 | 过显著线 | AUC | 确定性 |
|---|---|---:|---:|---:|---|
| 随机 | — | 1.3 | 0/5 | 0.500 | — |
| v3（997 次付费调用） | 3 | 3.0 | 0/5 | 0.497 | 否 |
| v4 初版 topiq，无资格门 | 3 | 3.0 | 0/5 | 0.606 | 是 |
| **+ 闭眼资格门** | 4/4/4/4/4 | **4.0** | **5/5** | 0.606 | **是** |
| + 换成 Apple Vision（我改的） | 3/4/3/3/4 | 3.4 | 2/5 | 0.734 | 否 |
| + 人脸大小分层 | 3/3/3/3/4 | 3.2 | 1/5 | 0.782 | 否 |

**我把默认换成 Apple Vision，理由是它 AUC 更高（0.729 vs 0.606）——
而我在这之前已经四次记录过「AUC 和交付会背离」，然后还是用了 AUC 当判据。**

三条证据都指向 topiq：

1. **交付更好且更稳**：4.0 / 5-5 显著，vs 3.4 / 2-5
2. **它是确定性的**；Apple Vision 同一批扫两遍 106/280 张分数不同，
   而「同样输入永远同样输出」是 v4 的核心主张
3. **换个数据集直接反过来**：道东三湖上 topiq 0.732、Apple Vision 只有 0.455

已改回 `face`（topiq_nr-face）。Apple Vision 保留为显式选项 ——
它在 K≥30 且开分层时更强（K=50 实测 8/20 vs 5/20）。

改回后端到端连跑三次：**4/20、p=0.0316、完全一致**。

> 这是本轮最该记住的一条：**判据错了，越努力越远。**
> 我用 AUC 优化了三轮，AUC 从 0.606 涨到 0.782，而交付从 4.0 掉到 3.2。

## 六、结论

**本地信号在人像上已经榨干了，而且瓶颈换了一个。** 最初以为是组内排序，
修完分组 bug 后发现真正的瓶颈是「Apple Vision 对小脸系统性低估」——
这个偏差能修（AUC 0.729 → 0.779），但增益落在 K=20 之下。

剩下的差距不是调参能补的：

- 排在 139 名之后的 8 张，需要理解「这是个好瞬间」
- 组内第 5–14 位的那几张，需要「这两张近乎相同的照片里哪张更好」

这两件事恰好是 v4 设计里**分配给 VLM 但从未实现**的部分。
而且第二件事正是 v3 的 AB/BA 双向盲比想解决的问题 ——
v3 失败是因为把它用在了绝对打分上，不是因为成对比较本身不成立。

**下一步（阻塞于 MiniMax 额度）**：

1. **组内成对比较实验**（约 30 组 / 60 次调用）——
   只在含多张候选的场景组内部问「这两张哪张更好」。
   这是本地信号最确定的短板，也是成本最低的验证。
2. **否决门误杀率实验**（约 40 次调用）—— 上线前必须先测。

在这两个实验做完之前，人像这条线的诚实结论是：
**4/20、p=0.032、确定性，比随机好 3.1 倍，成本为零。**
