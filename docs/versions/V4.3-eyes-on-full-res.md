# v4.3 · 眼部判定搬到原图

**一句话**：最强的本地信号之前在 68% 的照片上根本不存在，因为它跑在缩略图上。

## 起因：一批新标注

用户对 27 个连拍组（打乱后出成 35 题，含 8 组重复）做了标注，每题回答
「哪张最好 / 都差不多 / 都删除」，并写了理由。判据频次：

```
眼神        27/35 题  ██████████████████████████████
脸型光影      8/35 题  █████████
失焦         5/35 题  █████
构图引导物     4/35 题  ████
姿态         2/35 题  ██
表情         2/35 题  ██
```

对照 `compare.ts` 里给模型的判据清单（表情/眼神/姿态与手/人物关系）：

- **「眼神」压倒性主导**，而清单把它和其他三项并列
- 「脸型光影」「构图引导物」**完全不在清单里**
- 「人物关系」一次没出现（单人照）
- 「表情」只有 2 次，却被排在清单首位
- **提示词明令禁止用清晰度做判据，而用户 5/35 题在用失焦**

## 三处对既有结论的更正

| 之前报的 | 实际 | 为什么错 |
| --- | --- | --- |
| 组内选优提升 **2.29x** | **1.35x** | 随机基线按「每组只有一张正确答案」算。实测平均每组 4.3 张里有 1.74 张可接受，基线是 44% 不是 30% |
| VLM 通过线 **90%** | 天花板只有 **50%** | 用户重做同一组，「具体选哪几张」自我一致率 4/8。通过线定在了人类上限之上 40 个点 |
| 闭眼门「零误杀」 | 需限定范围 | 零误杀成立于「用户标注覆盖的 106 张内」，不是全部 309 张 |

## 根因

`minimumFaceAreaForEyeCheck = 0.008` 这个门槛本身没错 —— 引擎读的是 1024px
缩略图，那上面占画面 0.8% 的脸只有约 74px，关键点确实不可靠。

错在**它把分辨率写死了**。同一张脸在 7728×5152 的原图上有 564px：

```
面积 0.008 → 缩略图 74px（不可靠）  原图 564px（够）  覆盖 32%
面积 0.002 → 缩略图 37px（不可靠）  原图 282px（够）  覆盖 89%
```

瓶颈不是脸小，是**在缩略图上做检测**。

## 改动

1. 缩略图上定位人脸 → 按需从原图解出足够大的一版 → 裁出人脸（外扩 60%）→
   在 320px 的高清人脸上重做关键点
2. 门槛从「面积占比」换成「**人脸实际像素数**」（≥160px）—— 那才是关键点
   可靠性的决定量
3. 解码尺寸按人脸大小自适应，上限 8000px；缩略图上已经够大时不多解一次
4. 接入 Vision 的俯仰角，**把「闭眼」和「低头垂眼」解耦**

## 为什么必须解耦低头

眼睛纵横比（EAR）分不清「闭眼」和「低头」—— 低头时眼睑遮住大部分眼球，
EAR 同样掉到很低。

实测有一张用户自己选进精选的低头照，EAR 只有 0.095（20 张精选里最低，
次低 0.262，中间有巨大空档），但人眼一看眼睛是睁着的。它的 pitch 是 14°，
而正常平视的照片是 5–7°。

而**用户自己就是把这两件事分开判的**：标注里「眼睛都没睁开」和「低头看路
没有视觉引导物」是并列的两条理由。检测器不该把它们压成一个数。

注意：`pitch` 只有 `VNDetectFaceRectanglesRequestRevision3` 才给。默认
revision 下它恒为 nil，会静默拿到 nan。

## 低头**不做**一票否决

| 门 | 误杀（20张精选） | 误杀（35题可接受） | 挑50张交付 |
| --- | --- | --- | --- |
| 闭眼门 | **0/20** | **0/29** | 9/20 |
| 低头当门 | 2/20 | 1/29 | — |
| 两者合并 | 2/20 | 1/29 | 10/20 |

低头能让 K=50 从 9 提到 10，但代价是误杀 2 张用户的精选。
**误杀不可逆、漏杀可逆**，这个不对称压过那 1 张的收益。低头作为事实报出，不否决。

（低头照片的可接受率 5%，全体 27% —— 是强负相关信号，只是不够硬到能当否决。）

## 结果

```
                        改之前    改之后
眼睛读数覆盖率            32%      100%
用户标注范围内的覆盖       26%       97%
闭眼门拦下（106张内）      10张      21张
误杀 · 20张精选           0/20      0/20
误杀 · 35题可接受          0/29      0/29
挑50张交付               8/20      9/20   p=0.002
单张分析耗时             ~20s      ~24s
```

阈值 `0.22` 保持不动 —— 它当初只用一个人的六个样本标定，但在全覆盖数据上
恰好卡在最优边界：0.22 零误杀，0.25 就开始误杀 5 张。

## 否决掉的方案

**按连拍组归一化睁眼程度**（用来解决「眼睛天生细长的人被误判」）：

```
              AUC     当门用：误杀/拦到
绝对阈值      0.911        0 / 10
按组归一      0.740        1 / 7
```

按组归一**永远断言「这组里总有一张最好」**，而用户 35 题里 12 组是整组淘汰，
其中数组的理由正是「都没睁开眼」—— 按组归一会把某张闭眼照排到分位第一，
恰好毁掉最该拦下的情况。

正确的做法是**按「人」归一**（用这个人在整批里的分布，「整组都闭眼」仍测得出）。
但测试集基本是同一个人，按人归一 ≈ 全局归一 ≈ 与绝对阈值单调等价，
**在现有数据上验证不了**。

## 已知缺口

- **跨人眼型的鲁棒性没有证据**。阈值 0.22 在单人数据上表现好，但「眼睛天生细长
  的人是否被系统性误判」需要多人数据集才能证伪。这是真实存在的公平性风险。
- 只有一位标注者，全部结论建立在一个人的口味上。
- 阶段 2 的 VLM 成对评测（226 次调用）因两个模型路由都不可用而未跑：
  MiniMax 超出 Token Plan 用量、doubao 账户欠费。评测脚手架已就绪并冒烟验证过。

## 同期落地但未验证的

`ranker/photofilter_rank/stage2.py` + `tests/test_stage2.py`（14 个测试）：
组提取、成对考题生成、擂台赛。考题生成刻意做了「正确答案不能系统性排在
第一位」的保护并有测试守着。

验收设计从**组级改对级**：含金标的组只有 13 个，以基线 9/13 做精确二项检验，
连 12/13 都只有 p=0.057 —— 组级验收无论结果好坏都得不出结论。改成对级后
样本量 13 → 99。
