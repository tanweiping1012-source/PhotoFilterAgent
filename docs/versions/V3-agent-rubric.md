# v3 · 六维 rubric + 双向盲比 + 独立盲审

> 时间线：2026-08-22 ~ 08-29。这一版由 Codex 主导开发，是目前代码量最大、机制最完整的一版。
> 原始设计稿见仓库内 `README.CANDIDATE.md`（707 行）。本文是它的思路提炼 + 实测结果 + 事后诊断。

---

## 一、这一版要解决什么

v2 能出名单了，但留了两个洞：

1. **主 Agent 自己挑、自己说好，没有独立证据。**
2. **连拍组提前折叠**，一个选错的代表能埋掉一整组好照片。

v3 的目标写得很明确 —— 不再是「排除坏片」，而是：

> **在这整批照片里，应该留下哪几张？并且要能证明没有漏掉更好的。**

这是一个比 v2 难得多的问题。v2 只要判断单张的好坏，v3 要判断**集合的最优性**。

---

## 二、核心思路

一句话：**把「选片」当成一场有裁判、有申诉、有判决书的比赛来办。**

```
全池初评 → 决赛圈复看 → 关键对决 → 全局排名 → 有界多样性 → 独立盲审 → 判决书
 (低清)     (高清)      (双向盲比)  (BT聚合)              (子Agent找反例)  (receipt)
```

每一环都有一个明确要对抗的失败模式，这是这套设计里最见功力的部分。

---

## 三、七个环节，各自在防什么

### 1. 全池低清初评 —— 防「提前淘汰」

所有人像候选都要过一遍 512px 的评分，**包括同一连拍组里的每一张**。
不允许任何照片在被看到之前就出局。

这是对 v2 那个「闭眼代表」bug 的根本性修复：不是把代表选得更准，而是**取消代表制**。

预览规格是被严格冻结的：最长边 512px、保持原始比例不裁切、应用 EXIF 方向、
JPEG 质量 0.82、剥离全部元数据、只在内存生成。实测中位数 36KB。

### 2. 冻结的六维 rubric —— 防「模型每次换标准」

| 维度 | 权重 |
|---|---:|
| 人物瞬间（表情、眼神、姿态、人物关系） | 22% |
| 技术质量与主体可读性 | 18% |
| 构图与视觉层级 | 18% |
| 光线、色彩与影调 | 16% |
| 旅行语境与叙事 | 16% |
| 意图与完成度 | 10% |

**模型只返回六个分数，总分由本地按冻结权重重算。** 不让模型自己给总分 ——
否则每次调用的加权方式都可能不一样。

**资格判定极度克制**：只有四种情况能让照片失去资格（无法解码 / 没有有意拍摄的人物 /
主要人物状态无法解释 / 灾难性拍摄失败）。闭眼、侧脸、背影、剪影、运动模糊
**都不是自动淘汰条件** —— 因为这些恰恰可能是用户想要的风格。

> 事后看，这个克制是对的，但漏了一件事：闭眼**不该自动淘汰**，
> 但也不该像现在这样**完全不被检测**。代码里的注释写着「闭眼是故意不检的」，
> 结果是模型在低清预览上经常看不出闭眼。v4 把它放进了否决门，由用户决定要不要开。

### 3. 有界的用户偏好 —— 防「偏好变成另一套标准」

用户可以说「我喜欢自然抓拍、不看镜头的」。这句话被翻译成结构化参数，
但**只能让单张照片移动 ±4 分**，且不能救回资格不合格的照片。

baseline 分和 personalized 分分别保存，空偏好严格回到 baseline。

### 4. 冻结预算再执行 —— 防「边跑边加钱」

`build_selection mode=plan` **不发送任何图片**，先算出这一轮要花多少次高清复看、
多少次比较，冻结成一份计划；`mode=run` 只能执行这份计划。

K=20 时的预算：高清硬上限 60 张、成对比较最多 24 组（= 48 次调用）。

### 5. AB/BA 双向盲比 —— 防「模型的位置偏好」

同一对照片问两次：一次 A 在前，一次 B 在前。只有满足**全部**五个条件才算稳定胜者：

- 两个方向都不是平局；
- 归一化后指向同一张真实照片；
- 六维加权 margin 方向与胜者一致；
- 两方向平均绝对 margin ≥ 5 分；
- 两方向平均置信度 ≥ 0.75。

否则判平局。这是整个 v3 里最严谨的一个机制设计。

### 6. baseline 锚定的 Bradley-Terry —— 防「少量比较推翻全局」

Bradley-Terry 把稀疏的「谁赢谁」转成全局可比的能力分：

```
P(A 胜 B) = sigmoid(ability(A) − ability(B))
```

每张照片的 baseline 分先转成隐藏能力先验（`priorStrength=2`，最多 120 次迭代，限制单步更新），
所以少量成对比较只能局部纠偏。

> ⚠️ **这里藏着 v3 最关键的技术缺陷**，见第五节。

### 7. 独立盲审 audit_v3 —— 防「自己给自己发奖」

主 Agent 只能把**五项冻结输入**交给一个真正独立的子 Agent：
授权目录、候选范围、exact-K 名单、K、固定 seed。

不能传分数、理由、偏好、排名、任何中间状态。子 Agent 跑在独立会话里，
有自己的 prompt、rubric role、评分缓存和比较缓存。

四个阶段：
- **A** 入选的 20 张全部高清复看
- **B** 落选的全部低清覆盖
- **C** 固定 seed 抽样 + 切线挑战者 + 同组挑战者，提升到高清（上限 60）
- **D** 最强挑战者做最多 8 组 AB/BA

只要找到一张「明显更好却没入选」的照片，就是 FAIL，**只返回匿名的反例 ID**，
不返回审计方的分数或理由。主 Agent 必须用自己的标准重新评估这些照片。

## 四、为了让这套机制可信，额外造的东西

这部分是 v3 真正的工程量所在，而且**这些东西在 v4 里全部保留**：

| 机制 | 解决的问题 |
|---|---|
| 模型路由继承会话 | 不允许偷偷 fallback 到另一个模型；缓存身份绑定 provider/model/rubric hash |
| 调用前先写账本 | 中断后只补未完成的，不重跑已成功的 |
| 熔断器 | 401/403/429/额度错误立刻停链路，不在同一轮里烧 token |
| selection receipt | 绑定数据集指纹、名单哈希、rubric、实际模型、审计结果的判决书 |
| oracle 隔离 | 人工答案子目录必须在**枚举、指纹、匿名 ID 生成之前**排除 |
| 数据集预检 | 付费前先验证答案的每一张内容都还在候选池里，只输出汇总数字 |

代码规模：TypeScript 插件 7,566 行 + 测试 3,223 行 + Swift 引擎 2,926 行 ≈ 13,700 行。

## 五、实测结果

在 309 张人像 + 20 张人工精选的数据集上跑完整闭环：

```
付费调用          997 次
最终重合率        3/20
随机期望          1.31/20
超几何 p 值       0.133      ← 与运气区分不开
全局 AUC          0.497      ← 0.5 就是掷硬币
```

同时测了模型打分的**重复性**（同一张照片重新评分）：

```
309 张不同照片的总分标准差    6.72
同一张照片重评的噪声标准差    7.28   ← 比前者还大
金标与非金标的平均分差         +0.36
```

**一张照片跟它自己的差距，比它跟别的照片的差距还大。**

## 六、事后诊断：为什么是这个结果

### 直接原因：0–100 分这个输出形式本身不可靠

让视觉模型输出一个 0 到 100 的连续分，等于让它在一个没有锚点的标尺上做绝对判断。
模型每次调用都在重新想象这个标尺，于是 σ=7.28 的噪声就出来了。

而 309 张真实旅行照片，画质和构图水平本来就接近，真实差异只有 σ=6.72。
**信噪比小于 1，后面做什么都没用。**

### 放大原因：三个机制建在噪声上还不自知

**① Bradley-Terry 在洗自己的噪声。**
`ranking.ts` 里先验用 `logit(score/100)`，而初始值用的**也是同一个 score**。
等于让 BT 从噪声出发、再用噪声当先验 —— 它在数学上不可能比起点更好。
BT 本该是融合两个**独立**信号的工具，这里被用成了同一个信号的两次复述。

**② 多样性机制整个运行在噪声内部。**
多样性奖励上限 4 分，且只在「与最高分相差 4 分以内的质量前沿」里生效。
噪声是 7.28 —— 这个 4 分宽的前沿完全淹没在噪声里，所以它做的加权是随机的。

**③ 盲审报的失败，本身在测量误差里面。**
最后一次 audit FAIL 的 margin 是 6.6 分，而噪声 σ 是 7.28。
**审计判定的「明显更好」比它自己的测量误差还小。**
这意味着这套审计会源源不断地生产噪声工单，997 次调用里相当大一块花在这儿。

### 结构性原因：整套系统没有一处测量自己的信噪比

v3 有极其完整的**过程正确性**保障 —— 账本、熔断、缓存身份、隔离、receipt。
但从头到尾没有一个环节回答：**这个分数到底有没有信号？**

盲审看起来像是在做这件事，但它是**用同一个模型、同一套 rubric** 去审同一个模型的输出。
同源的偏差它审不出来，同源的噪声它也测不出来 —— 它只会把噪声当成分歧，然后要求重跑。

> 这是我认为 v3 最值得记住的教训：
> **验证「流程有没有被正确执行」和验证「流程有没有用」是两件完全不同的事。**
> v3 把前者做到了极致，而后者一次都没做。

### 一个附带发现：人机交互比 1.03

实测这一轮：**92 条人工指令 : 95 次工具调用**。几乎每一次工具调用都需要人推一下。

根本原因不是 agent 笨，是它**没有跨轮次的进度记忆** ——
每一轮醒来它都不知道上一轮做到哪、失败了几次、还剩多少，
于是分不清「正在慢慢推进」和「已经卡死了」，只能停下来等人判断。

Codex 那一轮的账本更直接：831 次付费调用里，**59 次是付了钱但失败的，6 次是零进展的**。

## 七、这一版留下了什么

**要保留的（v4 全部继承）：**
- 本机扫描 + 匿名化管线，原图只读
- oracle 隔离与数据集预检
- 冻结输入、结果可复现的凭证思路
- 「预算先冻结再执行」的成本可见性
- 「全池评估，不提前折叠」的原则

**要换掉的：**
- ❌ 让模型输出 0–100 绝对分 → 换成本地 embedding 排序
- ❌ BT 用同一个分数当先验和初值 → 先验换成独立的本地信号
- ❌ 在 4 分前沿内做多样性 → 先确认信噪比再谈多样性
- ❌ 同模型同 rubric 的盲审 → 换成对着人工答案的 AUC 测量

**要重新评估的（v3 没测过，v4 也还没测）：**
- 成对比较是否真的比绝对打分稳？文献说是，但这个数据集上没测过。
- 视觉模型做「否决」（闭眼、糊脸、切一半）的精度如何？没测过。

这两个问题各需要约 50 次调用就能回答，是 v4 之后最该做的实验。

---

## 八、公允地说

把 v3 写成「失败」是不准确的。

它作为**agent 工程**是成功的：子 Agent 隔离、五输入冻结、账本恢复、熔断、
凭证、oracle 隔离 —— 这套东西在 v4 里一行都没改，因为它们本来就是对的。

失败的是它中间那颗打分的心脏。而且，**正是因为 v3 把审计和测量做得足够严格，
这个失败才能被干净地定位出来** —— 997 次调用买到了一个确定的结论：
这条路在这个任务上不通。这个结论本身就是这一版最大的产出。
