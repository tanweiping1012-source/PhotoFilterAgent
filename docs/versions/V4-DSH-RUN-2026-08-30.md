## 一、隔离怎么做的

Codex 还在改 v3，所以 v4 必须完全不碰他的运行环境。

DSH 的全部状态（profiles、presets、sessions、credentials、缓存）都在 `$DSH_HOME` 下，
默认 `~/.dsh`。所以隔离只需要换一个 home：

```
~/.dsh          Codex 的 v3   ← 全程未被读写
~/.dsh-v4       v4 的         ← 本轮全部产物在这里
```

harness 的代码本身（`~/deepseek-harness`）是只读共享的，双方都不改它。

```
~/.dsh-v4/
├── settings.yaml                      从 ~/.dsh 复制（模型路由）
├── .credentials.yaml                  从 ~/.dsh 复制（循环模型要用）
├── ranker-venv/                       1.2GB Python 环境（torch/CLIP/pyiqa）
├── .agent-presets/photo-filter-v4/    Web UI 用的 preset
├── profiles/
│   ├── photo-v4/                      Web 界面
│   ├── photo-v4-headless/             一次性任务，本轮验证用的就是它
│   └── node_modules/@photo-filter-agent/dsh-photo-filter-v4 → 插件软链
└── photo-filter-v4/                   匿名编号映射（不进模型上下文）
```

启动：

```bash
cd ~/deepseek-harness
DSH_HOME=~/.dsh-v4 pnpm dsh --profile photo-v4            # Web 界面
DSH_HOME=~/.dsh-v4 pnpm dsh --profile photo-v4-headless "任务文本"   # 一次性
```

## 二、插件长什么样

`agent-v4/`，674 行 TypeScript，**6 个工具**（v3 是 18 个）：

| 工具 | 做什么 | 花钱吗 |
|---|---|---|
| `scan_folder` | 本地扫描、建数据集指纹、分配匿名编号 | 否 |
| `rank_photos` | 跑排序，返回前 K 张 | 否 |
| `explain_ranking` | 某几张为什么入选/落选；不给 ID 就看入选边界 | 否 |
| `set_my_favorites` | 记录用户喜欢的照片，下次排序学口味 | 否 |
| `evaluate_against_answer` | 有人工答案时测 AUC / 交付命中 / p 值 | 否 |
| `export_selection` | 两步确认，只复制 | 否 |

**整套工具集里没有一个会调用视觉模型。** 排序是本机的确定性函数，
agent 负责的是听懂意图、选参数、解释结果。

这正是 v4 的架构主张落到实处：v3 那 18 个工具里有一大半
（双向盲比、独立盲审、账本、熔断、凭证）是为了让噪声分数变得可信而建的。
分数不再有噪声，那些机制就不需要了。

安全边界与 v3 一致，而且同样是**结构约束而非承诺**：
profile 里关掉了 `tool-bash` / `tool-fs` / `tool-fs-search` / `skill-filesystem` /
`tool-str-replace-editor` / `tool-web`。v3 实测模型确实尝试过用 `read_image` 直接读原图
（全分辨率、带 EXIF 和 GPS）和用 `glob` 拿真实文件名。

## 三、四次运行

### 运行 1 · 冷启动选片

> 请从 …/eval-people-309 挑出最好的 20 张人像。没有额外偏好，先不要导出。

Agent 依次调用 `scan_folder` → `rank_photos`，返回 20 个匿名编号、分数、场景组，
并主动说明了三件事：走的是冷启动模式、**本轮付费模型调用 0 次**、
以及"想更贴合你的口味就标 10 张以上且要分散"。

耗时 1.5 秒（缓存命中）。名单映射回文件名后与人工精选重合 **3/20**。

### 运行 2 · 自带验收 —— 并且暴露了一个测量错误

让 agent 用人工精选清单验收。它报了 **4/20、p=0.032、显著**。

**这个数字是错的。** `evaluate_against_answer` 当时读的是"按分数取前 20"的命中，
而产品实际交付的 20 张还要过一道「同场景组最多入选 2 张」的限流。
真实交付是 **3/20、p=0.130、不显著**。

差的那一张查清楚了：

```
金标 DSCF9445  分数 +1.80  属于场景组 F0（共 6 张），组内第 4 名
F0 已入选 2 张：DSCF9452（+1.84，也是金标）、DSCF9449（+1.83，不是金标）
→ 限流把一张金标换成了一张非金标
```

**根因不是限流规则本身，是组内排序错了** —— F0 里排第 2 的非金标压过了排第 4 的金标。
另外查了一下：用户自己的 20 张落在 15 个场景组里、每组最多 2 张，
所以"同组最多 2 张"这个上限和用户行为是一致的，不是拍脑袋。
把上限放宽到 4 能拿到 4/20，但 3 vs 4 只差 0.9σ，不足以据此改默认值。

修法：`report()` 增加 `delivered_*` 三个字段，CLI 和插件都改成
**以交付名单为主指标**，排序数字降为次要并注明"不含限流"。

> 这是同一类错误的第三次出现，前两次记在
> [V4 设计文档](V4-local-first.md) 的「实验一点二五」。
> 共同点都是：**评测的对象和产品交付的对象不是同一个东西。**

### 运行 3 · 修复后重跑

同一个任务，agent 这次报的是：

```
交付命中        3/20    随机期望 1.29
超几何 p 值     0.1299  ⚠ 与运气区分不开
AUC            0.606
按分数前 20     4/20
头部提升        2.51x
候选 309 张 · 耗时 0.9s · 付费调用 0 次
```

并且它自己写道：

> v3（997 次付费调用）：AUC 0.497、交付 3/20、p=0.130
> v4（0 次付费调用）：AUC 0.606、交付 3/20、p=0.130
> 排序能力 v4 明显更好；但前 20 张交付在这个样本上跟 v3 打平。

**这是本轮最重要的结论，而且对 v4 不利：**
v4 在**交付的前 20 张**上并不比 v3 好，两者都是 3/20、p=0.13。
v4 确定的优势是 AUC（0.606 vs 0.497，用了全部 20×289 对，统计上稳得多）、
0 次付费调用、以及结果可复现。

### 运行 4 · 集中度护栏

给 agent 10 张**集中在旅程前半段**的标注（p017 p018 p025 p030 p033 p103 p111 p112 p163 p174）。

排序器算出集中度 1.14 > 1.05，**拒绝使用这批标注、退回冷启动**。
Agent 原样转达并解释了原因：

> 你标的 10 张集中在相邻的几个场景组（F63/F79/F83/F85/F86/F102/F104），
> 算法检测到集中度 1.14 > 1.05，拒绝使用标注、退回冷启动。
> 因为实测这种标注会让模型学成"像那个地方的照片"，AUC 反而掉到 0.439 ——
> 比不标（0.606）还差。报告里只能照实说"学口味"这一步没生效。

换成分散的 10 张（p017 p025 p033 p111 p163 p194 p205 p253 p266 p303）后，
护栏不再触发，模式切到 blend，AUC 0.793。
Agent 还自己补了一句样本量警告：剔除 10 张训练标注后只剩 10 张金标参与评测，
n=10 上的 1/10 下不了结论。

## 四、这轮验证了什么、没验证什么

**验证了：**
- 隔离有效：全程 `~/.dsh` 未被读写，Codex 的 v3 环境完好
- 6 个工具在真实 harness 上都能被 agent 正确调用
- 匿名编号机制有效：真实文件名一次都没进入模型上下文
- 集中度护栏在 agent 层完整生效，并且解释得清楚
- 「以交付为准」的测量修复后，agent 报的数字与本地复算一致

**没验证：**
- Web 界面（只跑了 headless）
- 导出流程的两步确认（没跑真实导出）
- 风景照片（只测了人像）
- 多轮对话中的状态保持（headless 是一次性进程，状态在内存里）
- 换一批照片、换一个用户

**一个诚实的提醒：** 这四次运行本身是要花钱的 —— 排序不花钱，
但 agent 的对话循环用的是 MiniMax-M3，每次任务几次模型往返。
"0 次付费调用"指的是**照片打分**这件事，不是整个会话免费。
