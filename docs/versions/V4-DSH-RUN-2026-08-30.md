> 2026-08-30。四次真实运行，用的是 `<照片目录>/eval-people-309`
> （309 张人像，20 张人工精选为答案，答案子目录在枚举阶段就排除）。

## 一、隔离怎么做的

Codex 还在改 v3，所以 v4 必须完全不碰他的运行环境。

DSH 的全部状态（profiles、presets、sessions、credentials、缓存）都在 `$DSH_HOME` 下，
默认 `~/.dsh`。所以隔离只需要换一个 home：

```
~/.dsh          Codex 的 v3   ← 全程未被读写
~/.dsh-v4       v4 的         ← 本轮全部产物在这里
```

harness 的代码本身（`~/deepseek-harness`）是只读共享的，双方都不改它。

```
~/.dsh-v4/
├── settings.yaml                      从 ~/.dsh 复制（模型路由）
├── .credentials.yaml                  从 ~/.dsh 复制（循环模型要用）
├── ranker-venv/                       1.2GB Python 环境（torch/CLIP/pyiqa）
├── .agent-presets/photo-filter-v4/    Web UI 用的 preset
├── profiles/
│   ├── photo-v4/                      Web 界面
│   ├── photo-v4-headless/             一次性任务，本轮验证用的就是它
│   └── node_modules/@photo-filter-agent/dsh-photo-filter-v4 → 插件软链
└── photo-filter-v4/                   匿名编号映射（不进模型上下文）
```

启动：

```bash
cd ~/deepseek-harness
DSH_HOME=~/.dsh-v4 pnpm dsh --profile photo-v4            # Web 界面
DSH_HOME=~/.dsh-v4 pnpm dsh --profile photo-v4-headless "任务文本"   # 一次性
```

## 二、插件长什么样

`agent-v4/`，674 行 TypeScript，**6 个工具**（v3 是 18 个）：

| 工具 | 做什么 | 花钱吗 |
|---|---|---|
| `scan_folder` | 本地扫描、建数据集指纹、分配匿名编号 | 否 |
| `rank_photos` | 跑排序，返回前 K 张 | 否 |
| `explain_ranking` | 某几张为什么入选/落选；不给 ID 就看入选边界 | 否 |
| `set_my_favorites` | 记录用户喜欢的照片，下次排序学口味 | 否 |
| `evaluate_against_answer` | 有人工答案时测 AUC / 交付命中 / p 值 | 否 |
| `export_selection` | 两步确认，只复制 | 否 |

**整套工具集里没有一个会调用视觉模型。** 排序是本机的确定性函数，
agent 负责的是听懂意图、选参数、解释结果。

这正是 v4 的架构主张落到实处：v3 那 18 个工具里有一大半
（双向盲比、独立盲审、账本、熔断、凭证）是为了让噪声分数变得可信而建的。
分数不再有噪声，那些机制就不需要了。

安全边界与 v3 一致，而且同样是**结构约束而非承诺**：
profile 里关掉了 `tool-bash` / `tool-fs` / `tool-fs-search` / `skill-filesystem` /
`tool-str-replace-editor` / `tool-web`。v3 实测模型确实尝试过用 `read_image` 直接读原图
（全分辨率、带 EXIF 和 GPS）和用 `glob` 拿真实文件名。

## 三、四次运行

### 运行 1 · 冷启动选片

> 请从 …/eval-people-309 挑出最好的 20 张人像。没有额外偏好，先不要导出。

Agent 依次调用 `scan_folder` → `rank_photos`，返回 20 个匿名编号、分数、场景组，
并主动说明了三件事：走的是冷启动模式、**本轮付费模型调用 0 次**、
以及"想更贴合你的口味就标 10 张以上且要分散"。

耗时 1.5 秒（缓存命中）。名单映射回文件名后与人工精选重合 **3/20**。

### 运行 2 · 自带验收 —— 并且暴露了一个测量错误

让 agent 用人工精选清单验收。它报了 **4/20、p=0.032、显著**。

**这个数字是错的。** `evaluate_against_answer` 当时读的是"按分数取前 20"的命中，
而产品实际交付的 20 张还要过一道「同场景组最多入选 2 张」的限流。
真实交付是 **3/20、p=0.130、不显著**。

差的那一张查清楚了：

```
金标 DSCF9445  分数 +1.80  属于场景组 F0（共 6 张），组内第 4 名
F0 已入选 2 张：DSCF9452（+1.84，也是金标）、DSCF9449（+1.83，不是金标）
→ 限流把一张金标换成了一张非金标
```

**根因不是限流规则本身，是组内排序错了** —— F0 里排第 2 的非金标压过了排第 4 的金标。
另外查了一下：用户自己的 20 张落在 15 个场景组里、每组最多 2 张，
所以"同组最多 2 张"这个上限和用户行为是一致的，不是拍脑袋。
把上限放宽到 4 能拿到 4/20，但 3 vs 4 只差 0.9σ，不足以据此改默认值。

修法：`report()` 增加 `delivered_*` 三个字段，CLI 和插件都改成
**以交付名单为主指标**，排序数字降为次要并注明"不含限流"。

> 这是同一类错误的第三次出现，前两次记在
> [V4 设计文档](V4-local-first.md) 的「实验一点二五」。
> 共同点都是：**评测的对象和产品交付的对象不是同一个东西。**

### 运行 3 · 修复后重跑

同一个任务，agent 这次报的是：

```
交付命中        3/20    随机期望 1.29
超几何 p 值     0.1299  ⚠ 与运气区分不开
AUC            0.606
按分数前 20     4/20
头部提升        2.51x
候选 309 张 · 耗时 0.9s · 付费调用 0 次
```

并且它自己写道：

> v3（997 次付费调用）：AUC 0.497、交付 3/20、p=0.130
> v4（0 次付费调用）：AUC 0.606、交付 3/20、p=0.130
> 排序能力 v4 明显更好；但前 20 张交付在这个样本上跟 v3 打平。

**这是本轮最重要的结论，而且对 v4 不利：**
v4 在**交付的前 20 张**上并不比 v3 好，两者都是 3/20、p=0.13。
v4 确定的优势是 AUC（0.606 vs 0.497，用了全部 20×289 对，统计上稳得多）、
0 次付费调用、以及结果可复现。

### 运行 4 · 集中度护栏

给 agent 10 张**集中在旅程前半段**的标注（p017 p018 p025 p030 p033 p103 p111 p112 p163 p174）。

排序器算出集中度 1.14 > 1.05，**拒绝使用这批标注、退回冷启动**。
Agent 原样转达并解释了原因：

> 你标的 10 张集中在相邻的几个场景组（F63/F79/F83/F85/F86/F102/F104），
> 算法检测到集中度 1.14 > 1.05，拒绝使用标注、退回冷启动。
> 因为实测这种标注会让模型学成"像那个地方的照片"，AUC 反而掉到 0.439 ——
> 比不标（0.606）还差。报告里只能照实说"学口味"这一步没生效。

换成分散的 10 张（p017 p025 p033 p111 p163 p194 p205 p253 p266 p303）后，
护栏不再触发，模式切到 blend，AUC 0.793。
Agent 还自己补了一句样本量警告：剔除 10 张训练标注后只剩 10 张金标参与评测，
n=10 上的 1/10 下不了结论。

### 运行 5 · Web 界面 —— 又暴露一个设计问题

在 Web UI 里跑同样两步（选片 → 给集中的标注）。

第一步 10 秒、3 步、2 次工具调用完成。Agent 主动说明了付费 0 次、模式、
场景组分布（20 张来自 14 个组，6 个组各 2 张），以及"分数是相对值不是百分制"。

第二步给它集中的标注。有意思的是 **agent 在调用工具之前就自己察觉了**：

> 注意一下分散度：你标的 10 张里，p017/p018/p025/p030/p033 看起来在编号上比较靠前，
> 可能集中在同一段行程附近。如果它们确实来自同一个场景/地点，重排效果会反向变差。

护栏随后确认了这一点。但 agent 接着不得不解释一个**我设计错了的行为**：

> 前 10 张全部是你标过的那 10 张（"霸占"了入选位）……
> p017 和 p030 这种排在第 1、第 4 的，**分数是 0.00** —— 不是它"特别好"

原因：`rank.py` 里有一条"用户亲口说喜欢的照片直接置顶"的逻辑，
但护栏刚刚判定这批标注**不可信**，置顶却照做了。
结果是把"我们不信任的信号"伪装成了排序结论，而且置顶项的分数是 0.00，毫无意义。

修法：抽出 `pinned_labels(mode, label_idx)`，护栏退回 cold 时返回空列表 ——
**标注只在被采纳时才置顶**。

> 这个问题只有把 agent 真跑起来、看着它费力解释自己的输出才会暴露。
> 单元测试测不出来，因为它测的是每个函数各自对不对，
> 而这里错的是两条各自正确的逻辑撞在了一起。

### 运行 6 · 「全程没有 VLM？」—— 一个提问引出的最大漏洞

被问到「似乎全程没有 VLM？」。答案是对的：**没有任何 VLM 看过照片，一张都没有。**

- CLIP 是图像**编码器**，把图片变成 768 个数字，不生成语言、不回答问题
- topiq_nr-face / laion_aes 是打分用的小 CNN
- MiniMax-M3 是 LLM，但它读到的是 `p266 分数+1.84 场景组F0` 这样的文本行

所以准确说法是：**有 LLM，没有 VLM。** LLM 负责听懂意图、选参数、解释结果。

v4 的设计里 VLM 本来有位置 —— 只做否决（闭眼、脸糊、切一半），
但只写了设计没实现。这个缺口有多大，拿 v1 的免费闭眼检测量了一下：

| | 闭眼张数 |
|---|---|
| **v4 选出的 20 张** | **6 张（30%）** |
| 全池基准率 | 8.2% |
| **用户自己挑的 20 张** | **0 张** |

**v4 选闭眼照的比例是基准率的 3.7 倍，而用户一张都不要。**
20 个名额里有 6 个浪费在了绝不会被接受的照片上。

**而这件事根本不需要 VLM。** 闭眼检测是 v1 就写好的免费本地能力
（Apple Vision 给眼睛轮廓坐标，自己算高宽比，阈值 0.22）。
v4 把排序主干挪回本地时，**连同 v1 那层免费的资格门一起丢掉了**。

补上之后（`ranker/photofilter_rank/eligibility.py`）：

```
关掉资格门（改之前）  交付 3/20   p=0.1299  ⚠ 与运气区分不开
打开资格门            交付 4/20   p=0.0316  ✅ 统计显著
```

**从「跟运气区分不开」跨到「统计显著」，代价是零 —— 纯本地、不联网、不花钱。**

设计上做成**默认开、可以关、并且如实报告拦下了几张**，而不是硬淘汰：
v3 的 rubric 里写着「闭眼不是自动淘汰条件」，理由是闭眼可能是有意的风格，
这个顾虑是对的；但实测这个用户的精选里闭眼 0 张，对他而言就是硬伤。
所以由用户决定，不替他做死。

引擎不可用时**报错而不是静默跳过** —— 用户以为有资格门保护时，必须知道它没生效。

> 这一条是本轮性价比最高的修复，而且它来自一个提问，不是来自测试。
> 教训：**「我们不用 VLM」不等于「不需要 VLM 负责的那件事」。**
> 把主干挪回本地的时候，很容易连带把旧方案里正确的部分一起扔掉。

### 运行 7 · 顺着「没有 VLM」继续查，v4 的核心卖点被推翻了

补上闭眼资格门之后，顺手量了一下 v1 那些「被否掉」的本地指标各自的区分力：

| 指标 | AUC | 信噪比（照片间σ / 重评σ） |
|---|---:|---:|
| **Apple Vision 人脸质量** | **0.72** | **13.94 / 0.66 = 21.2** |
| CLIP + topiq_nr-face（v4 原来用的） | 0.61 | — |
| 全局清晰度 | 0.52 | — |
| v3 的六维付费打分 | 0.50 | 6.72 / 7.28 = 0.92 |

**v1 就有的免费指标，比我 v4 精心搭的 CLIP 流水线更强。**
v1 的结论「本地技术指标和人的口味基本无关」把它一起否掉了 ——
那个结论对清晰度/曝光成立（AUC 0.517），对人脸质量不成立。
全局清晰度与人脸质量的相关系数只有 −0.318，本来就是两件事。

**为什么一个端上小 CNN 能赢过付费大模型**：
苹果那个模型（`VNDetectFaceCaptureQualityRequest`）被训练来回答的正好是
「同一张脸的多次拍摄里哪一次更好」——用于实况照片选关键帧、连拍选最佳。
而我们的测试集就是 309 张同一趟旅行、同几个人的照片，
「这一组近乎相同的人像里哪张最好」**就是它的训练目标本身**。
通用美学模型被训练的是「任意图片好不好看」，是另一个问题。

**任务足够窄的时候，任务对口的小模型 > 通用大模型。** 信噪比差了 23 倍。

换上之后又暴露两处非确定性，都得修：

**① 分组依赖打分。** 贪心 leader 聚类按分数顺序处理，换打分器就换一套分组。
实测同一份打分只改分组顺序，交付在 3~5/20 之间跳。
改成按文件名顺序 —— 分组是照片本身的属性，不该随打分变化。

**② Apple Vision 的人脸质量本身不是确定性的。**
同一批扫两遍，106/280 张分数差 1–5 分，检出人脸数 276 vs 282。
（闭眼判定倒是完全稳定：27 vs 27。）信号是好的（信噪比 21.2，
三次扫描 AUC 0.689/0.694/0.689），但前 20 名这条切线对 ±1 分极度敏感。
修法：按数据集指纹缓存引擎结果。缓存后连跑三次完全一致。

### 运行 8 · 个人口味探针：一个必须承认的负面结果

冷启动从 0.606 提到 0.723 之后，重新标定「标几张才值得启用个人口味」：

```
标注数    探针 AUC    冷启动    胜过冷启动
  3       0.555     0.725        0%
  5       0.610     0.729        5%
 10       0.673     0.724       28%
 15       0.713     0.699       53%
```

纯探针到 15 张才勉强打平。但探针和 vision_face 是**真互补**
（一个学内容偏好，一个测人脸拍摄质量），融合后 AUC 确实更好：

```
探针权重 w      m=5     m=10    m=15
0.0 纯冷启动    0.721   0.720   0.739
0.4~0.5        0.735   0.749   0.795   ← AUC 最优
1.0 纯探针      0.603   0.666   0.721
```

**然后按同一组留出金标测交付前 20：**

```
方案                  交付前20命中      AUC
冷启动（忽略标注）      1.83 ± 0.97     0.714
融合 0.55/0.45        1.57 ± 0.80     0.754

融合胜过冷启动 7/30 次，打平 13 次，落后 10 次
```

**AUC 更高，交付没有改善，甚至略差。** 这和之前融合两个通用美学指标
是同一个模式：全局排序变好，头部被稀释。

**结论：v4 最初的核心卖点「从你的标注里学口味」，在交付层面没有可测收益。**
所以它默认关闭 —— 标注仍然被记录，但不参与排序，
并且 agent 必须如实告诉用户「标了不会更准」，不许粉饰成「正在学习你的口味」。

代码和测量都留着，因为这个负面结果本身就是产出。

## 四、这轮验证了什么、没验证什么

**验证了：**
- 隔离有效：全程 `~/.dsh` 未被读写，Codex 的 v3 环境完好
- Web 界面可用：preset 正常出现在选择器里，两轮对话共 6 步、工具调用 5.5 秒
- 6 个工具在真实 harness 上都能被 agent 正确调用
- 匿名编号机制有效：真实文件名一次都没进入模型上下文
- 集中度护栏在 agent 层完整生效，并且解释得清楚
- 「以交付为准」的测量修复后，agent 报的数字与本地复算一致

**最终成绩（eval-people-309，连跑三次完全一致）：**

```
交付命中        4/20    随机期望 1.29
超几何 p 值     0.0316  ✅ 统计显著
AUC            0.723
头部提升        2.83x
候选 309 张 · 付费调用 0 次

对照 v3：997 次付费调用 → 交付 3/20，p=0.1299 ⚠ 与运气区分不开
对照 v4 早期（无资格门 + CLIP/topiq）：交付 3/20，p=0.1299，AUC 0.606
```

**没验证：**
- 导出流程的两步确认（没跑真实导出）
- 风景照片（只测了人像）
- 多轮对话中的状态保持（headless 是一次性进程，状态在内存里）
- 换一批照片、换一个用户

**一个诚实的提醒：** 这四次运行本身是要花钱的 —— 排序不花钱，
但 agent 的对话循环用的是 MiniMax-M3，每次任务几次模型往返。
"0 次付费调用"指的是**照片打分**这件事，不是整个会话免费。
